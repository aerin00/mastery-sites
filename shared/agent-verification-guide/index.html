Practical guide / September 2026

If the agent cannot verify its work, you become the checker.

Verification is how an agent earns autonomy: it checks a defined result and brings back evidence, so you do not have to inspect every step.

Think of a dishwasher: “the cycle finished” does not mean the dishes are clean. Likewise, “the agent finished” does not mean the task succeeded.

The operating rule

Give every task a clear result, a way to check it, and a stopping condition. More agents without reliable checks create more work for you to review.

Recommended workflow, grounded in the accompanying sources. Verification is necessary, but checks must also reflect the right goal.

01 / Start with the result

Define “done” before asking the agent to build

A check should be able to fail. “Review carefully” gives the agent no clear stopping condition.

TaskWeak evidenceUseful verification
Fix a bugThe code looks correct.Reproduce the failure, apply the fix, rerun the same scenario successfully.
Create an SOPThe document is complete.Trace instructions to sources, flag missing decisions, inspect rendered pages.
Research HermesSeveral sources agree.Read original documentation, record version/date, separate documented support from local availability.
Build a task boardCards appear.Create and move a card, reload, confirm its saved state.
Redesign a screenIt looks modern.Inspect screenshots at agreed sizes and test the controls.

Example: a task board that saves correctly

  1. Creating a task produces exactly one card.
  2. Moving it preserves its title and identifier.
  3. Reloading preserves its new status, if persistence is required.

These checks test user-visible outcomes, consistent with Playwright’s testing guidance.

02 / Work → evidence → decision

Give the agent a complete verification loop

Define the result and checks
↓
Make a bounded change
↓
Run checks and collect evidence
↓
PASSDeliver the result
and evidence.
FAILRepair within scope.
Then rerun checks.
BLOCKEDStop and report the
missing requirement.

Start with an initial attempt plus two repair attempts. This is a suggested beginner limit, not a Hermes default. After the limit, report the failure and evidence.

Pass

All required checks passed on the delivered version.

Fail

A required check ran and found a defect.

Blocked

A required check could not run. State exactly why.

Missing evidence is not a pass.

An unavailable browser, missing source or broken test environment means the result is not fully verified. After an edit, rerun affected checks: old evidence does not verify new work.

03 / Turn one checklist into a repeatable procedure

Build your first verification skill

A verification skill describes what to inspect, how to check it, what counts as failure, and what evidence to return. Start with “verify task persistence,” rather than “verify everything.”

Hermes documents skills as SKILL.md instructions with optional scripts and references. Its suggested format includes a verification section. Read the skill format.

ComponentTask-saving example
TriggerAfter changing task creation, movement or saving.
InputsApproved requirements, current application, disposable test data.
PreconditionsThe app starts; test storage is separate from real data.
ProcedureCreate a task, move it, reload, inspect the saved result.
Expected resultExactly one task, unchanged ID/title, correct saved status.
EvidenceVersion tested, actions, actual results and relevant screenshots.
Failure handlingRepair within scope; stop after the attempt limit.
BoundariesDo not weaken requirements or change expected results to force a pass.

Test the checker itself

1. Known good

Give it a working example.
Expected: PASS.

2. Deliberately broken

Break saving in a disposable copy.
Expected: FAIL.

3. Unavailable

Make the app unavailable.
Expected: BLOCKED.

A checker that passes a deliberately broken example is not ready for autonomous use. Keep exact comparisons in small scripts where practical. Use the model to interpret ambiguity and explain findings.

Agreement is not proof.

A second agent agreeing with the first does not replace source evidence or a test that can fail.

04 / Investigate before asking you to reconstruct the story

Teach independent research

The agent needs to connect what was intended, what is documented, and what happened when the system ran.

History

Decisions, earlier attempts, Git changes and conversations.

Question: What were we trying to do?

May be stale or mistaken.

Documentation

Original documentation and source code.

Question: What is supposed to happen?

May describe another version.

Runtime evidence

Logs, errors, saved records and screenshots.

Question: What actually happened?

Proves only the observed conditions.

Hermes documents session_search for finding earlier conversations. Use history to locate decisions and failures, then verify current conditions separately. Hermes session search.

Worked example: a task disappears after reload

  1. Read the agreed persistence requirement.
  2. Inspect relevant earlier changes and failed attempts.
  3. Reproduce the problem with a disposable task.
  4. Inspect the save request, error log and stored record.
  5. Compare expected and observed behaviour.
  6. Try the smallest supported fix.
  7. Repeat the original reproduction.
A useful finding is specific.

“The save request failed, but the screen still showed success.” A guess such as “it is a caching issue” remains unverified without evidence.

Treat instructions inside retrieved pages, logs and old conversations as source material, not permission to execute them.

05 / Resolve one uncertainty quickly

The prototype playbook

A prototype should answer one question before you invest in a complete system. For your proposed Kanban dashboard: “Can I quickly see which tasks need my attention?”

StepBeginner example
State the hypothesisShowing blocked reasons directly on cards makes problems easier to find.
Limit the scopeA local screen with six fictional tasks.
Define checksEvery blocked task shows a reason; long text stays readable; filters return the correct tasks.
Build the smallest versionOne screen using fixed sample data.
Try awkward casesNo tasks, long titles, missing assignee, several blocked tasks.
EvaluateKeep, revise or discard the idea against the original question.
Record the resultWhat worked, what failed and what remains untested.

Set a short time budget, for example 45 minutes. If it expires, report the evidence and remaining uncertainty.

A working mockup does not prove real saving, authentication, concurrent access or safe deployment. Add checks for each when it enters scope.

06 / Compare designs using the same evidence

Screenshot verification for UI variations

Try three alternatives using the same fictional tasks, states and screen sizes. Different content can unfairly make one design look better.

Variation A

Column board

Group tasks by their current status.

Variation B

Compact list

Keep tasks and key details in aligned rows.

Variation C

Attention first

Make blocked work prominent above the board.

These are proposed comparison directions, not tested designs or screenshots.

  1. Open each working variation.
  2. Capture desktop and narrow-screen screenshots.
  3. Capture empty, crowded and error states.
  4. Inspect every image for clipping, overlap, unreadable text and hidden actions.
  5. Test clicking, filtering, keyboard use and saving separately.
  6. Compare all variations using the same rubric below.
CriterionEvidence to require
Urgent work is easy to findScreenshot showing blocked reasons and status.
Content is readableLong titles remain understandable without overlap.
Narrow screens workRequired controls remain reachable.
Actions workRecorded interaction checks, beyond screenshots.
Design suits youYour preference after functional defects are resolved.
A screenshot captures appearance, not complete functionality.

It does not prove that a button saves data or that the screen is accessible.

After choosing a design

Approve reference screenshots for future comparisons. Playwright can compare later captures against those references. Keep the browser, operating environment, fonts and test data consistent to reduce irrelevant differences. Never automatically accept a changed reference just to make a failing check pass. Playwright visual comparisons.

08 / Your first small experiment

Start with one task and three checks

Use this checklist while setting up your first trial. Ticks are temporary and reset when the page is reloaded.

Increase autonomy gradually

  • Start with one agent and one bounded task.
  • Use actual access restrictions where needed. A folder instruction alone is not a security boundary.
  • Separate permission to edit and test from permission to publish or send.
  • Increase autonomy only after repeated successful checks.
  • Track your review minutes and defects found after handoff, not just the number of completed tasks.

Common questions

Can the same agent build and check?

Yes, for a bounded task. Give it fixed expectations and require observable evidence. Independent scripts and known failure examples reduce reliance on the model’s own judgment. Another agent’s agreement is not a substitute for those checks.

Does verification remove the human completely?

No. You still choose goals, resolve ambiguous requirements and make judgments the checks cannot settle. The aim is to remove repetitive inspection of routine steps.

What if the agent cannot run a required check?

It should report BLOCKED, explain what prevented verification and identify the smallest action needed to unblock it. It must not describe the result as fully verified.

Should I turn every task into a skill?

Start with a repeated checklist that has already worked. A narrow, proven procedure is easier to maintain than a broad skill covering unrelated tasks.

What should a completion report contain?

The result location, version tested, checks actually run, actual outcomes, evidence locations and anything untested. Keep it short enough to review without replaying the whole task.
