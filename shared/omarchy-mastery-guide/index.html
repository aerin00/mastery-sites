Omarchy / Mastery Reference

Make Omarchy your primary OS without fighting what makes it good.

Use Omarchy as an opinionated, keyboard-first Arch workstation. Keep the coherent defaults where they help, replace only the pieces that solve a real problem, and build your agentic workflow around terminal-native tools, Git, containers, and reproducible configuration.

Arch LinuxHyprlandQuickshellWaylandNeovimDockerMiseAI agents
Best default strategy: spend your first week learning Omarchy’s intended workflow before replacing core pieces. The fastest way to turn Omarchy into a worse Windows clone is to immediately install a full desktop environment and re-create every Windows habit.

01 / Mental model

The main shift is not “Windows commands vs Linux commands.” It is moving from app-centric desktop use to a composable system where the shell, files, services, keybindings, and agents are first-class interfaces.

Windows: app first

Open a GUI, click through menus, store state inside the app.

Omarchy: workflow first

Use keybindings, terminal tools, text config, Git, and small composable programs.

Windows: global installs

Installers and registry state often accumulate invisibly.

Omarchy: declarative-ish habits

Package manager + dotfiles + project files make your environment reproducible.

Windows: one desktop

Floating windows and taskbar are the organizing model.

Omarchy: workspaces

Hyprland workspaces become contextual “rooms” for browser, code, agents, docs, and monitoring.

05 / Commands worth learning

These give you disproportionate leverage. Learn the mental model, not just the syntax.

Packages

sudo pacman -Syu            # full system update
pacman -Ss ripgrep           # search official repos
sudo pacman -S ripgrep       # install package
pacman -Qi ripgrep           # package information
sudo pacman -Rns PACKAGE     # remove package + unused deps (review carefully)

Files and search

pwd                         # where am I?
ls -lah                     # files including hidden files
cd ~/Projects               # move to a directory
cp source target            # copy
mv old new                  # move / rename
rm file                     # delete file
rm -r folder                # ⚠ recursive delete, verify path first
fd config ~/.config         # fast filename search
rg "needle" .               # fast text search
du -sh * | sort -h          # what is consuming disk space?

Processes and services

ps aux | rg PROCESS
pgrep -af PROCESS
kill PID
systemctl status SERVICE
sudo systemctl enable --now SERVICE
journalctl -u SERVICE -b
journalctl -b -p warning    # current boot warnings/errors

Network and disks

ip addr
ip route
ss -tulpn
lsblk -f
df -h
mount | column -t

Environment

echo $PATH
env | sort
which python
type python
mise current
mise use python@3.13

Git daily loop

git status
git diff
git add -p
git commit -m "feat: concise description"
git log --oneline --graph --decorate -20
gh auth status
gh repo view --web
lazygit
Risky commands: treat `rm -rf`, `sudo`, disk partitioning, filesystem formatting, `chown -R`, `chmod -R`, and broad `pacman -R` operations as destructive. Read the target twice before pressing Enter.

06 / Workflows worth adopting

Workspace by context

Use one Hyprland workspace for docs/research, one for editor, one for agents, one for app preview, one for logs/monitoring. This feels more natural than constantly alt-tabbing.

Agent + verifier pattern

Let one agent implement, then use tests, linters, `git diff`, and optionally a second model as verifier. Do not treat “agent says done” as evidence.

Project command surface

Add a `justfile`, `Makefile`, or `Taskfile` with stable commands: `setup`, `dev`, `test`, `lint`, `smoke`, `build`, `release`.

Version your thinking

Keep `README.md`, `AGENTS.md`, `ROADMAP.md`, ADRs, prompts, and runbooks in the repo so future agents inherit project context.

Use containers for dependencies

Prefer Docker Compose for Postgres, Redis, queues, and other infrastructure rather than polluting your host OS.

Keep local knowledge agent-readable

Markdown notes, code, shell scripts, and text configuration are easy for both you and agents to search, diff, and modify.

08 / Customize safely

  • Keep changes small and reversible.
  • Version your dotfiles before heavy customization.
  • Prefer Omarchy’s own install/default menus where available.
  • Change one core component at a time, then use the system for a day.
  • Keep a known-good terminal available before changing shells or terminal emulators.
  • For Hyprland, add user overrides rather than rewriting vendor config wholesale where possible.
  • Use Git commits as checkpoints before editing complicated config.
  • Prefer project-local dependencies and containers over global pollution.
Useful pattern: `copy config → commit → change → reload → verify`. If something breaks, the diff tells you exactly what changed.

09 / First 7 days

Day 1Learn workspaces, `Super` shortcuts, terminal launch, browser, clipboard history, screenshots.
Day 2Learn `pwd`, `ls`, `cd`, `cp`, `mv`, `rm`, `fd`, `rg`, `fzf`, `zoxide`.
Day 3Learn `pacman`, `systemctl`, `journalctl`, `btop`, `lsblk`, `df`.
Day 4Set up GitHub CLI, SSH keys, `lazygit`, dotfiles repo, and a `~/Projects` convention.
Day 5Use Mise + Docker Compose in one real project. Add a `justfile`.
Day 6Run one coding agent end-to-end: plan → edit → test → diff → commit.
Day 7Review friction. Replace only the defaults that caused repeated problems.

10 / Common traps and recovery

  • Replacing the desktop too early: if you install KDE/GNOME immediately, you may bypass the workflow Omarchy is designed to teach.
  • Blind AUR installs: AUR packages are community build recipes. Read the package page and PKGBUILD for sensitive tools.
  • Partial upgrades: on Arch, avoid piecemeal system upgrades. Use a full `pacman -Syu` workflow.
  • Editing system config without backups: prefer user config, then version it.
  • Running Docker as root casually: understand the security tradeoff before joining the `docker` group.
  • Assuming X11 advice applies: Omarchy is Wayland-first. Old Linux tutorials may use outdated Xorg tools.
  • Agent trust: never let an agent’s prose substitute for test output, logs, or `git diff`.
  • Windows-only dependency creep: keep a Windows VM as an escape hatch rather than making it the center of your workflow.

Recovery commands

git diff ~/.config/...             # inspect dotfile change
git restore PATH                   # restore tracked config file
journalctl -b -p err               # current boot errors
systemctl --failed                 # failed services
pacman -Qk PACKAGE                 # verify package files
pacman -Qo /path/to/file           # which package owns this file?
sudo pacman -S PACKAGE             # reinstall package if needed
