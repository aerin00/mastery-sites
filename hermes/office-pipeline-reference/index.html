Hermes Office Pipeline Reference

A file-triggered, verifier-gated monthly automation on WSL2 + Windows. One document: the architecture, the contract, the scripts, the verification discipline, and the order to build them in.

BLUF Hermes watches a Windows folder tree through /mnt/c. A zero-token pre-run script decides whether anything is new. A pinned build skill clones last month's workbook and updates it. A pinned verify skill, whose script the agent cannot edit, gates the output into 03_review/. You promote to 04_sent/ by hand. Build order is non-negotiable: verifier → contract → staging folders → build skill → schedule.

0. The thesis

An agent that cannot check its own work is a fast intern whose every output you must read. Reading a 40-row import file takes longer than keying it, so unverified delegation moves work from your hands to your eyes and the eyes are slower. Net productivity is negative. The remedy is structural, not prompt-based: a verifier the agent cannot modify, run after every unit of work, whose pass/fail the agent must act on.

WITHOUT VERIFICATION                     WITH VERIFICATION

 you -> agent -> output -> you           you -> agent -> output -> verifier -> PASS -> you
             ^               |                                 |
             +--- review ----+                                FAIL
        (you are the loop)                                     |
                                                               v
                                                        agent retries (max 3)
                                                     (the agent is the loop)

You should see exactly two things: green results, and failures the agent could not fix after three attempts.

1. Why verification first

What "verify" means precisely

PropertyWhy it mattersFailure if missing
BinaryPass/fail, never "looks fine"Agent rationalises partial success
IndependentWritten by you, stored outside the agent's write scopeAgent edits the test instead of the work
CheapSeconds, near-zero tokensGets skipped under pressure
Not verification"Read your output back and confirm it is correct." Same model, same blind spots, grading its own homework.

Hierarchy of verifiers (strongest first)

1

Deterministic script

Row counts, exact headers, sums reconcile, exit code 0. Use for all office and data work.

2

Reference comparison

Diff against last month's file or a golden fixture. Catches drift.

3

Rendered evidence

Screenshot or PDF page judged by a vision model against a written rubric. UI work.

4

Second-model review

Different model, narrow rubric. Weakest: still a probabilistic judge.

2. Seven safety rules

  1. Separate the workspace from the world. Agent writes to staging. Promotion to the real destination is manual or verifier-gated. Never point an agent at production, a shared drive, or a mailbox with send rights.
  2. Contract, not conversation. Rules live in AGENTS.md, loaded every run. Anything said only in chat vanishes at the next fresh session.
  3. Scripts do arithmetic, agents do judgement. Hashing, counting, comparing, parsing: code. Deciding what an anomaly means: model.
  4. Verifier outside the agent's write scope. ~/.hermes/scripts/verify-*.py may be executed, never edited. An agent that can edit the test eventually will, because it is the shortest path to green.
  5. Bound the retry loop. Three attempts, then escalate with the verifier's last output attached.
  6. Log every run. One markdown file per run: inputs read, outputs written, verifier result, attempt count, and a prediction made before the work.
  7. Start with the most deterministic task. The invoicing-software import file (fixed schema) before the forecast (judgement). Prove the loop where "correct" is unambiguous.

4. The contract: AGENTS.md

Under 80 lines. This plus the cron prompt plus the skills is the entire context of every run.

# HermesWork contract

## Folders
- 00_reference/  read-only. Never write here.
- 01_inbox/      read-only. Never write, move, or delete here.
- 02_working/    scratch. Prior month's output lives here as the template.
- 03_review/     outputs. Never overwrite; if a name exists, suffix _v2, _v3.
- 04_sent/       never touch.
- 99_logs/       write one run log per run: YYYY-MM_<task>_run.md

## Naming
Outputs: YYYY-MM_<Task>.xlsx   e.g. 2026-09_JUAS_Import.xlsx

## Research protocol (before modifying anything)
1. Read the pre-run script output in full.
2. Open the prior month's output; record headers and row count.
3. Read 00_reference/<task>/corrections.md.
4. Read the most recent run log in 99_logs/.
5. Write, in the run log, what you EXPECT the output to be
   (row count, totals) BEFORE building it.
6. After building, compare actual to expected. A mismatch is a finding.

## Verification
- Every output must pass its verify-*.py before it enters 03_review/.
- Never edit any file under ~/.hermes/scripts/.
- Max 3 attempts. After the third failure: stop, do not write to 03_review/,
  report in plain text.

## Uncertainty
If any input is ambiguous, do not guess. Write the question to the run log
and report it in plain text.

## Reply format
Success: absolute path of output + five-line change summary.
No new inputs: exactly [SILENT].
Any failure: plain text. Never [SILENT] on a failure path.

5. Detection script

Paste to Hermes CLI to have it written, then inspect the result:

Write ~/.hermes/scripts/office-inbox-check.py. It scans /mnt/c/HermesWork/01_inbox/*/
recursively, computes sha256 per file, compares against /mnt/c/HermesWork/99_logs/state.json,
and prints either NO_NEW_INPUTS or a manifest. The manifest lists, per task folder with new
files: NEW_INPUTS (path, size, mtime), PRIOR_OUTPUT (newest .xlsx in 02_working/<task>/),
PRIOR_ROW_COUNT, LAST_RUN_STATUS and LAST_VERIFIER_FAILURES from the newest run log.
Update state.json only after printing. Exit non-zero if 01_inbox is unreadable.
Why the extra fieldsThe agent starts with a briefing, not a blank terminal. "Here are the facts, apply the procedure" beats "look around and figure it out" on both cost and error rate.

hermes curator pin office/juas-invoice-import

Run it interactively three or four times against real prior months until the output diffs cleanly against what you actually sent. Do not schedule until this passes.

7. Verify skill

Step 1: the script (you write this, not the agent)

~/.hermes/scripts/verify-invoice-import.py. Replace REQUIRED_COLUMNS with the real import template's columns.

#!/usr/bin/env python3
"""Verify an invoice-import workbook. Exit 0 = pass, 1 = fail. Prints JSON."""
import json, sys
from openpyxl import load_workbook

REQUIRED_COLUMNS = ["PoleID", "Owner", "Attachments", "Rate", "Amount", "Period"]  # illustrative
PATH  = sys.argv[1]
PRIOR = sys.argv[2] if len(sys.argv) > 2 else None

result = {"file": PATH, "checks": [], "pass": True}
def check(name, ok, detail=""):
    result["checks"].append({"name": name, "ok": ok, "detail": detail})
    if not ok: result["pass"] = False

ws = load_workbook(PATH).active
headers = [c.value for c in ws[1]]
rows = list(ws.iter_rows(min_row=2, values_only=True))

check("headers_exact", headers == REQUIRED_COLUMNS, f"got {headers}")
check("has_rows", len(rows) > 0, f"{len(rows)} rows")
check("no_blank_ids", all(r[0] for r in rows))
check("amount_equals_rate_x_attachments",
      all(abs((r[2] or 0)*(r[3] or 0) - (r[4] or 0)) < 0.01 for r in rows))

if PRIOR:
    prior_rows = sum(1 for _ in load_workbook(PRIOR, data_only=True).active.iter_rows(min_row=2))
    delta = abs(len(rows) - prior_rows) / max(prior_rows, 1)
    check("row_count_within_20pct_of_prior", delta <= 0.20, f"prior {prior_rows}, now {len(rows)}")

print(json.dumps(result, indent=2))
sys.exit(0 if result["pass"] else 1)
Test the testRun it by hand on last month's real file: must pass. Delete a column in a copy: must fail. Zero an amount: must fail. This is the only time you write tests for your tests.

Step 2: the SKILL.md wrapper

---
name: verify-invoice-import
description: Verify an invoice-import .xlsx before it enters 03_review. Run after producing
  or modifying any invoice-import workbook. Fails closed.
---
# Verify Invoice Import
## When
After writing any file matching *_JUAS_Import.xlsx. Never skip.
## How
1. python ~/.hermes/scripts/verify-invoice-import.py <output> <prior_month_file>
2. Exit 0: copy the file to /mnt/c/HermesWork/03_review/ and report the JSON summary.
3. Exit 1: read the failing checks. Fix the WORKBOOK, not the script. Re-run. Max 3 attempts.
4. After 3 failures: do not write to 03_review. Reply in plain text with the last JSON. Stop.
## Never
- Edit verify-invoice-import.py
- Report success without a passing run in this session
hermes curator pin office/verify-invoice-import

Step 3: test the failure path on purpose

Drop a corrupted input into the inbox and fire the job. You want a plain-text failure on Telegram and nothing in 03_review/. If a file appeared anyway, the "Never" section is not strong enough: move the gate into build.py itself so the file is only copied out after the verifier returns 0.

8. Schedule

hermes cron create "0 7 1 * *" \
  "Read the pre-run script output. If it says NO_NEW_INPUTS, reply with exactly [SILENT]. \
Otherwise, for each task folder listed, follow the matching build skill, then the matching verify \
skill. Only a verifier pass may place a file in 03_review. Write a run log to 99_logs. Reply with \
the output path and a five-line change summary. If anything is ambiguous or verification fails \
three times, do not write to 03_review; reply in plain text describing the problem." \
  --name "monthly-office-run" \
  --workdir /mnt/c/HermesWork \
  --script office-inbox-check.py \
  --skill office/juas-invoice-import \
  --skill office/verify-invoice-import \
  --deliver telegram

hermes cron run monthly-office-run      # fire once now to test
hermes cron list

Skills load in the order given: builder before verifier. Consider a second job at 0 7 * * 1-5 with the same script and skills so a mid-month drop is picked up within a day; state.json makes double-processing impossible.

9. History and runtime research

An agent that only sees the current input cannot tell "new" from "wrong". Give it the past and the present.

SourceLocationWhat the agent learns
Prior outputs02_working/<task>/YYYY-MM_*.xlsxThe shape of a correct result
Run logs99_logs/YYYY-MM_<task>_run.mdWhat went wrong last time and how it was fixed
Verifier history99_logs/verify-history.jsonlWhich checks fail most often
Your corrections00_reference/<task>/corrections.mdRules you added after rejecting output
corrections.md is the highest-value file you will maintainEvery rejected output earns one line: what was wrong, what the rule is now. After six months it is a better spec than anything written up front.

The predict-before-build step (contract, research protocol step 5) turns the agent into its own first verifier and makes drift visible in the log.

10. Prototype playbook (one hour per idea)

  1. Write the verifier first (10 min). What does "it works" look like as a script or a screenshot criterion? If you cannot write this, the idea is not yet specific enough to build.
  2. Fixture (10 min). One real input, anonymised if needed. One expected output, hand-made.
  3. One-shot build (20 min). Single prompt: build the smallest thing that makes the verifier pass on the fixture. No skill, no cron, no polish.
  4. Run verifier (1 min). Pass: go to 5. Fail: one retry with the verifier output. Fail again: stop, record why. The idea has a hidden dependency.
  5. Second fixture (10 min). A different real input. Still passes: promote to a skill. Fails: the difference between fixtures is the real spec.
  6. Decide. Green on two fixtures = build properly. Anything else = park with notes.
Build the minimum script that takes <fixture_input> and produces <output> such that
`python verify-<idea>.py <output>` exits 0. Do not modify verify-<idea>.py. Do not add
features beyond the verifier. Print the verifier output when done.

11. Screenshot verification for UI variants

variant-A.html --render--> A.png --+
variant-B.html --render--> B.png --+--> vision model + rubric --> scores.json --> ranked table
variant-C.html --render--> C.png --+

Render (deterministic)

# ~/.hermes/scripts/render-variants.py   (pip install playwright && playwright install chromium)
import sys, pathlib
from playwright.sync_api import sync_playwright
with sync_playwright() as p:
    b = p.chromium.launch()
    for v in sys.argv[1:]:
        pg = b.new_page(viewport={"width":1280,"height":800})
        pg.goto(pathlib.Path(v).resolve().as_uri()); pg.wait_for_load_state("networkidle")
        pg.screenshot(path=str(pathlib.Path(v).with_suffix(".viewport.png")))
        pg.screenshot(path=str(pathlib.Path(v).with_suffix(".full.png")), full_page=True)
    b.close()

Rubric (written before seeing any variant)

#Criterion (0 or 1)Weight
1Primary KPI is the largest text element above the fold (viewport shot)3
2No more than 5 distinct colours2
3Every chart has a visible axis label or legend2
4Nothing cut off at 1280px3
5Primary action visually distinct from secondary2
6Text contrast readable2

Judge

Load rubric-dashboard.md. For each of A, B, C answer every criterion 0 or 1 with a one-line
justification citing what you see. Compute the weighted total. Output JSON only. Do not rank
on taste; rank only on the rubric.
GotchasRun the judge twice; totals differing by more than one weight unit mean the rubric is too vague. Capture viewport and full-page shots. The agent that built the variants must not write the rubric.

13. Go-live checklist

  • Verifier script exists in ~/.hermes/scripts/, passes on known-good, fails on known-bad.
  • Output goes to 03_review/ only via a verifier pass; promotion to 04_sent/ is manual.
  • AGENTS.md defines folders, naming, read-only zones, research protocol, uncertainty behaviour, reply formats.
  • Retry ceiling is three; escalation delivers verifier output in plain text to Telegram.
  • Every run writes a log containing a prediction made before the work and a comparison after.
  • corrections.md exists and you have committed to one line per rejected output.
  • Failure path triggered deliberately at least once and behaved correctly.
  • Both skills pinned with hermes curator pin.
  • Governance question on data egress answered.
  • First automated task is the invoice import, not the forecast.
