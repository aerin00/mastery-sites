02 / FIELDCRAFT

Small moves, sharper agent

Operational details that separate a demo from a dependable daily system.

01

Capture the successful procedure, not the whole transcript

Use /learn after a workflow has passed its acceptance check. Ask for a lean skill with prerequisites, pitfalls, and verification, placing longer material in reference files loaded on demand.

02

Keep memory compact and search history for detail

Keep durable conventions in bounded memory and use session_search for actual prior conversations. A promise to remember is not a persisted write: check the tool result, pending approvals, active profile and exact file. Memory snapshots refresh at a new session. For replace, old_text selects the whole entry; content must preserve all still-valid parts. A staged replace or remove is now pinned to the entry it targeted and is refused if that entry changed, so clear stale pending writes instead of approving them. /journey is a learning timeline, not an inventory of unused installed skills.

03

Give repository cron jobs an explicit workdir

The cron documentation says jobs are detached from repository context by default. Set an existing absolute workdir when approving a project job so its tools and project instructions resolve against the intended repository.

04

Check delivery separately from job execution

Verify an approved test at the intended destination; saved output is not delivered notification. The current cron guide documents a 60-second default standalone-send deadline and warns that a timed-out message may still arrive if already accepted. Read the destination receipt before retrying. Jobs created from request/response api_server sessions use a home-channel fallback for deliver: origin. These guide behaviors were not runtime-tested here.

05

Do not share one Hermes home between independent agents

The memory documentation warns that concurrent agents sharing a Hermes home can compound each other's automatic writes. Give independent agents separate profiles and verify the active scope before changing skills, memory, or scheduled jobs.

06

Make recurring inference selection deliberate

The current cron guide says resolution is per-job pin, then cron.model/cron.model_provider, then the main model at fire time, so without either override changing the main default retargets unpinned jobs. It now also says a pinned job never walks the global fallback_providers chain: pinning buys route certainty and gives up outage fallback, while credential-pool rotation within one provider still applies to every job. The guide documents --pin/--unpin and user-requested pinned=true/false through cronjob_manage; an agent cannot choose a different model. Verify installed-version semantics and obtain approval before changing routing.

07

Run /new at natural boundaries on messaging platforms

The memory documentation now explains that the whole system is built around session end: MEMORY.md and USER.md carry essentials into the next session, and session_search fills the gaps once old context is gone. On messaging platforms where a chat is one continuous session surviving restarts, never resetting means compaction runs over an ever-longer history and the learning loop rarely fires. Run /new at finished tasks, topic changes, or the start of a day so memory pays off.

08

Recurring failures alert once; ack only what you mean

A cron job failing repeatedly with the same error pings once and then reminds on a cooldown, with a distinct incident per error signature. A successful run resolves open incidents, while acknowledging one closes it for that exact signature only. Run `hermes cron doctor` for a read-only fleet health check and `hermes cron incidents` for durable failure records.

Released in v0.21.5: the gateway --replace fixes that stop units from defeating the host lock

released · Every unit generated by hermes gateway install runs gateway run --replace, and after the v0.21.4 host-wide lock that flag was skipping the very arbitration the lock exists for. ae16316 restricts the PID-claim bypass to --force, because a --replace unit that saw no owner could start a second gateway beside the multiplexer and fight it over the same bot tokens. 516687d makes --replace target the host owner only when that owner serves this profile or its served set is unknown, after a live macOS launchd fleet on 0.21.4 respawn-stormed on 'Refusing --replace'. 6c51f86 with follow-ups 41f0bd9 and 1a4da74 retires the Hermes-authored systemd 20-replace.conf drop-in on unit refresh while keeping an operator-written file of the same name. The September 24 check confirmed by repository comparison that all of these commits are contained in the v2026.9.24 tag, so availability moves from merged-unreleased to released. The tagged build was not exercised locally.

Only --force skips it now. A --replace that took the owner over already freed the lock with that process, so real takeovers are unchanged.

If several profiles run their own gateway units, an installed build older than 0.21.5 still has the lock without these corrections: watch for restart loops or token contention there. Read unit files and gateway status read-only; do not edit units, force-replace a running owner, or upgrade production hosts merely to pick up this entry.

Cron guide: a pinned job never walks the global fallback-provider chain

documented-unverified · A newly documented rule makes pinning and outage resilience an explicit trade-off. A job with its own provider, model or base_url (set with --provider/--model, --pin, the dashboard, or jobs.json) never falls back to fallback_providers or the legacy fallback_model: when the pinned route fails the run fails and the failure alert says so, the same rule subagent delegation applies to a pinned child. Credential-pool rotation within the same provider still applies to every job, pinned or not. The guide states that before this rule a pinned job could silently run on the first working fallback entry, and tells anyone who relied on that to unpin (hermes cron edit <job_id> --unpin) and set the model through cron.model. The same retrieval added a sparse-schedule quota recovery: if a provider reopens at least half a schedule period before a sparse job's next natural occurrence, one blocked occurrence retries at that boundary, while dense schedules, manual runs and interval jobs keep their natural next run. Documentation evidence only; not tested against an installed build.

A job with its own provider, model or base_url ... never falls back to the global chain.

Inventory which recurring jobs are pinned before assuming a configured fallback chain protects them, and decide per job whether route certainty or outage survival matters more. Verify installed-version behavior read-only and keep pin/unpin changes user-approved. Resolution order (per-job pin, then cron.model/cron.model_provider, then the main model at fire time) is summarized in the pin-recurring-inference tip.

Memory guide: a staged replace or remove is pinned to the exact entry it targeted

documented-unverified · The approval gate gained a correctness guarantee worth knowing before trusting queued memory edits. A staged replace or remove, which the background review stages even with the gate off, now records the full entry it targets and shows it in /memory pending. Approval applies to exactly that entry: if the entry changed after the write was staged, the write is refused and stays pending for rejection, and a replace/remove staged before this pinning existed has no verifiable target and is refused too, so it must be rejected and recreated. /memory approve lists the full text of every entry it overwrote or removed. This sits on top of the existing rule that old_text locates the whole entry and content replaces it, so a partial replacement can still discard facts meant to survive. The same retrieval changed journey memory chunk ids to memory:<source>:<index>:<fingerprint>, to be passed back exactly as printed. Documentation clarifications, not runtime-tested findings.

Approval applies to exactly that entry: if it changed after the write was staged, the write is refused and stays pending for you to reject.

Clear out any long-pending memory writes rather than approving them blindly, and expect pre-existing staged replacements to be refused. Read back the exact profile-local file after an approved write instead of trusting the approval message alone.

Skills guide: the installer has no --no-skills flag; opt out at setup or afterwards

documented-unverified · The previous skills guide told readers to pass --no-skills to install.sh for an empty default profile. The September 25 retrieval corrects that: the installer has no --no-skills flag. Its setup stage asks whether to seed the bundled catalog when Blank Slate setup is chosen, and answering no writes the .no-bundled-skills opt-out marker; non-interactive installs seed the catalog, so hermes skills opt-out must be run afterwards to keep the profile empty. Named profiles still accept hermes profile create <name> --no-skills. On any installed profile, hermes skills opt-out only stops future seeding, --remove deletes bundled skills only when byte-identical to the installed version (edited, hub-installed and self-written skills are kept), and hermes skills opt-in --sync re-seeds. Anyone scripting unattended installs from the old instruction would have silently received the full catalog. Documentation correction, not tested against an installed build.

the installer has no --no-skills flag. Its setup stage asks whether to seed the bundled catalog when you pick the Blank Slate setup

If a profile was meant to start empty from an unattended install, check read-only for the .no-bundled-skills marker in that profile directory before assuming the catalog was skipped. Prefer plain hermes skills opt-out over --remove, and keep any profile skill changes user-approved.
