02 / FIELDCRAFT

Small moves, sharper agent

Operational details that separate a demo from a dependable daily system.

01

Capture the successful procedure, not the whole transcript

Use /learn after a workflow has passed its acceptance check. Ask for a lean skill with prerequisites, pitfalls, and verification, placing longer material in reference files loaded on demand.

02

Keep memory compact and search history for detail

Hermes memory is bounded and injected into the prompt; session_search retrieves actual stored conversations when specifics are needed. Keep durable preferences and conventions in memory rather than logs, transcripts, or temporary debugging state.

03

Give repository cron jobs an explicit workdir

The cron documentation says jobs are detached from repository context by default. Set an existing absolute workdir when approving a project job so its tools and project instructions resolve against the intended repository.

04

Check delivery separately from job execution

Hermes supports local output and configured messaging targets, which are not interchangeable. Specify the intended destination and verify an approved test run reaches it rather than assuming a saved output means a notification arrived.

05

Do not share one Hermes home between independent agents

The memory documentation warns that concurrent agents sharing a Hermes home can compound each other's automatic writes. Give independent agents separate profiles and verify the active scope before changing skills, memory, or scheduled jobs.

06

Make recurring inference selection deliberate

The current cron guide describes per-job pins, then a cron-level default, then creation-time provider/model snapshots for otherwise unpinned jobs; jobs predating snapshots still follow the live global default. Verify installed-version behavior and let the user approve inference routing explicitly rather than assuming a chat-model switch retargets or stops unattended jobs.

v0.21.1 is the new tagged patch release

released · The September 7 release supersedes the previous edition's v0.21.0 release listing and rolls up cron scheduling/delivery, MCP authorization, startup, and delegation work. The release notes defer full curated feature details to v0.22.0; they do not verify every later documentation claim.

The rollup includes the codebase modularization, file-operation and startup performance work, provider and model updates, desktop session controls and browser annotations, MCP authorization improvements, cron scheduling and delivery fixes, and delegation reliability improvements.

Compare the installed version with this tag before planning an approved update; managed deployments should use their deployment tooling. Do not assume September 11 main-branch fixes are in this September 7 release.

Cron model-selection guidance now describes creation-time snapshots

documented-unverified · The current guide's model-selection section differs from the earlier drift-guard tip: otherwise unpinned jobs with snapshots keep their creation-time provider/model when the chat default changes. Per-job pins and the cron-level default take precedence; older jobs without snapshots still follow the live default. Installed-version behavior was not tested.

An unpinned job stays on the provider/model it was created under, so changing your chat model never changes (or stops) your cron fleet.

Review each job's resolved route read-only on the installed version before any user-approved inference change. A chat-model change alone is not a reliable way to retarget scheduled jobs.

Supporting source ↗

Main-branch session lookup stops silently scanning other profiles

merged-unreleased · Commit df0eed4 removes the cross-profile fallback after a session-ID miss and keeps explicit profile-qualified lookup available. This matters for evidence-backed project recall across separate profiles. It appears on main after the latest collected release, not as a verified capability of every installed build.

A miss now stays a miss, with a hint to name the owning profile (profile=<name> / @session:<profile>/<id>), which remains the sanctioned, explicit cross-profile read.

Keep project-recall requests scoped to the intended profile. If a session is missing, do not silently search other profiles; name a different profile only when the user has authorized that scope.
