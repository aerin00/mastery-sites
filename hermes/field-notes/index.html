02 / FIELDCRAFT

Small moves, sharper agent

Operational details that separate a demo from a dependable daily system.

01

Capture the successful procedure, not the whole transcript

Use /learn after a workflow has passed its acceptance check. Ask for a lean skill with prerequisites, pitfalls, and verification, placing longer material in reference files loaded on demand.

02

Keep memory compact and search history for detail

Keep durable conventions in bounded memory and use session_search for actual prior conversations. A promise to remember is not a persisted write: check the tool result, pending approvals, active profile and exact file. Memory snapshots refresh at a new session. For replace, old_text selects the whole entry; content must preserve all still-valid parts. A staged replace or remove is now pinned to the entry it targeted and is refused if that entry changed, so clear stale pending writes instead of approving them. /journey is a learning timeline, not an inventory of unused installed skills.

03

Give repository cron jobs an explicit workdir

The cron documentation says jobs are detached from repository context by default. Set an existing absolute workdir when approving a project job so its tools and project instructions resolve against the intended repository.

04

Check delivery separately from job execution

Verify an approved test at the intended destination; saved output is not delivered notification. The current cron guide documents a 60-second default standalone-send deadline and warns that a timed-out message may still arrive if already accepted. Read the destination receipt before retrying. Jobs created from request/response api_server sessions use a home-channel fallback for deliver: origin. These guide behaviors were not runtime-tested here.

05

Do not share one Hermes home between independent agents

The memory documentation warns that concurrent agents sharing a Hermes home can compound each other's automatic writes. Give independent agents separate profiles and verify the active scope before changing skills, memory, or scheduled jobs.

06

Make recurring inference selection deliberate

The current cron guide says resolution is per-job pin, then cron.model/cron.model_provider, then the main model at fire time, so without either override changing the main default retargets unpinned jobs. It now also says a pinned job never walks the global fallback_providers chain: pinning buys route certainty and gives up outage fallback, while credential-pool rotation within one provider still applies to every job. The guide documents --pin/--unpin and user-requested pinned=true/false through cronjob_manage; an agent cannot choose a different model. Verify installed-version semantics and obtain approval before changing routing.

07

Run /new at natural boundaries on messaging platforms

The memory documentation now explains that the whole system is built around session end: MEMORY.md and USER.md carry essentials into the next session, and session_search fills the gaps once old context is gone. On messaging platforms where a chat is one continuous session surviving restarts, never resetting means compaction runs over an ever-longer history and the learning loop rarely fires. Run /new at finished tasks, topic changes, or the start of a day so memory pays off.

08

Recurring failures alert once; ack only what you mean

A cron job failing repeatedly with the same error pings once and then reminds on a cooldown, with a distinct incident per error signature; the guide says signatures ignore case, whitespace and measured durations such as 'idle for 603s', so a timeout that varies only in seconds stays one incident. A successful run resolves open incidents, while acknowledging one closes it for that exact signature only. Run `hermes cron doctor` for a read-only fleet health check and `hermes cron incidents` for durable failure records.

Memory guide: Honcho and Supermemory leave the bundled set and install from the plugin catalog

documented-unverified · The October 2 retrieval of the memory guide now says Hermes ships 5 external memory provider plugins (OpenViking, Mem0, Holographic, RetainDB and ByteRover), with Honcho, Hindsight and Supermemory available from the plugin catalog via hermes plugins install <name>; the previous day's text listed 7 bundled providers including Honcho and Supermemory. Same-day main-branch commits carry this out: 7e53b3e removes the bundled Honcho provider and 87be434 removes the bundled Supermemory provider, whose message explains a catalog entry stays dormant while a bundled copy exists, so deleting the in-tree copy lets the update-time migration install the catalog version for every home whose memory.provider names it. Follow-up commits warn every profile whose memory provider is unavailable (c687e36), keep one profile's refused migration from skipping others (c5b3d66), ask once per update (a5144c7), limit headless install consent to providers that left core (0be2d56), and name the install command when a catalog provider is missing (d450c36). Separately, 501590a unlists the RetainDB, ByteRover and Holographic catalog entries, stating Nous Research will not maintain memory providers; their bundled copies are unchanged. These main-branch commits are not in any tag yet. Documentation and commit evidence only; not tested against an installed build.

Hermes ships with 5 external memory provider plugins — OpenViking, Mem0, Holographic, RetainDB and ByteRover — and more, such as Honcho, Hindsight and Supermemory, are available from the plugin catalog

Built-in MEMORY.md and USER.md are unaffected. Keep plugin installs on production profiles user-approved.

Cron guide: Python script and monitor_script jobs can pin a user-managed venv via --interpreter

documented-unverified · The September 28 retrieval of the cron guide adds venv pinning to the script-interpreter rules. Non-.sh scripts run under the current Python interpreter (sys.executable); a Python script or monitor_script that needs packages the Hermes runtime doesn't carry can now pin a user-managed venv by passing --interpreter ~/venvs/.../bin/python at create/edit time, with the linked 'Using your own Python environment' section for setup. Constraints are unchanged and explicit: the Hermes-managed venv stays Hermes-owned and nothing is installed or restored automatically, scripts must still resolve inside $HERMES_HOME/scripts/ (relative, absolute, and ~-prefixed paths accepted only when the resolved target stays in that directory; escaping paths are rejected), and the subprocess environment remains sanitized so provider API credentials and other Hermes-managed secrets are not inherited by cron scripts. Documentation evidence only; not tested against an installed build.

can also pin a user-managed venv (for packages the Hermes runtime doesn't carry) by passing --interpreter ~/venvs/.../bin/python at create/edit time

If a cron script needs a third-party package the runtime lacks, create the venv yourself outside Hermes, then set --interpreter on the job at create or edit time rather than pip-installing into the Hermes-managed venv. Verify the script still resolves inside $HERMES_HOME/scripts/ and remember secrets are not inherited, so any credential the script needs must be declared through the documented env-passthrough.

Cron guide: a malformed jobs.json is repaired on load instead of stopping the scheduler

documented-unverified · The September 27 retrieval of the cron guide adds a paragraph after the existing tip to manage jobs through cronjob_manage, hermes cron edit or /cron rather than patching jobs.json. If a hand edit leaves jobs.json malformed, the scheduler now repairs it on the next load instead of stopping: entries in the jobs list that are not JSON objects are dropped, and a repeat.completed value that is not a non-negative integer is reset to a valid count (0 when it cannot be read). Each repair is logged as a warning that records value types only, never contents. Same-day main-branch commits add the matching guard on save: c642f42 refuses to overwrite a corrupt jobs store, 758ad51 fails closed inside the merge peek while keeping merges for mergeable repairs, and 553388b re-checks disk before an unmergeable repair replaces the store. Those save-side guards are untagged main-branch changes. Practical reading: a bad hand edit should no longer halt every scheduled job, but a dropped malformed entry is a silently missing job unless someone reads the warning. Documentation and commit-title evidence only; not tested against an installed build.

Each repair is logged as a warning (value types only, never contents).

Keep editing jobs through the cron tool or CLI. After any manual jobs.json edit, list jobs and compare the count with what you expect, and check the scheduler log for repair warnings, because a dropped malformed entry will not announce itself on the messaging side.

Skills guide: Desktop Browse tab and hermes:// install links from the Skills Hub

documented-unverified · The September 26 retrieval adds a 'Browse and install in Desktop' section. Capabilities -> Skills in Desktop now switches between Installed, which reads the selected profile's actual skills and enabled state, and Browse, a native catalog UI. Desktop and the public Skills Hub read the same published CDN snapshot (/docs/api/skills.json), generated at docs build time from bundled skills, optional-skills and the centralized index; browsing does not crawl GitHub or query marketplaces live. Each installable Skills Hub card gains an Install in Hermes button that opens Desktop with a source-qualified target such as hermes://skill/install?identifier=official%2Fsecurity%2F1password. Desktop shows a confirmation with separate Source and Install to rows; Cancel changes nothing, and installation goes through the existing Skills Hub pipeline including security scanning and action logs. A link cannot bypass scanning or select a different profile, changes apply to new sessions, and the route requires an updated Desktop build (otherwise copy the card's CLI command). Bundled skills without an explicit target in an older snapshot get no install link rather than an ambiguous bare-name resolution. Documentation evidence only; not tested against an installed build.

Installation uses the existing Skills Hub pipeline, including security scanning, action logs, and installed-list refresh.

With several profiles, check the Install to row before confirming: a web link installs into whichever profile Desktop currently has selected. If the link is not recognized, check the installed Desktop version rather than forcing the CLI path, and keep skill installs on production profiles user-approved.
