02 / FIELDCRAFT

Small moves, sharper agent

Operational details that separate a demo from a dependable daily system.

01

Capture the successful procedure, not the whole transcript

Use /learn after a workflow has passed its acceptance check. Ask for a lean skill with prerequisites, pitfalls, and verification, placing longer material in reference files loaded on demand.

02

Keep memory compact and search history for detail

Keep durable conventions in bounded memory and use session_search for actual prior conversations. A promise to remember is not a persisted write: check the tool result, pending approvals, active profile and exact file. Memory snapshots refresh at a new session. Since v0.22.0 there is no replace action: patch swaps one unique span inside an entry and keeps the rest, and each call names its target store; builds before v0.22.0 still have replace, which overwrites the whole matched entry. v0.22.0 also turns on sessions.auto_prune, deleting ended sessions inactive for 90 days at startup, so set sessions.auto_prune: false if session_search must reach older history. When memory is full, the guide now says the error states how many characters to free; retry as one operations batch that removes or shortens stale entries and adds the new one, since the limit is checked on the batch result. A staged write is pinned to the entry it targeted and is refused if that entry changed, so clear stale pending writes instead of approving them. /journey is a learning timeline, not an inventory of unused installed skills.

03

Give repository cron jobs an explicit workdir

The cron documentation says jobs are detached from repository context by default. Set an existing absolute workdir when approving a project job so its tools and project instructions resolve against the intended repository.

04

Check delivery separately from job execution

Verify an approved test at the intended destination; saved output is not delivered notification. The current cron guide documents a 60-second default standalone-send deadline and warns that a timed-out message may still arrive if already accepted. Read the destination receipt before retrying. Jobs created from request/response api_server sessions use a home-channel fallback for deliver: origin. These guide behaviors were not runtime-tested here.

05

Do not share one Hermes home between independent agents

The memory documentation warns that concurrent agents sharing a Hermes home can compound each other's automatic writes. Give independent agents separate profiles and verify the active scope before changing skills, memory, or scheduled jobs.

06

Make recurring inference selection deliberate

The current cron guide says resolution is per-job pin, then cron.model/cron.model_provider, then the main model at fire time, so without either override changing the main default retargets unpinned jobs. It now also says a pinned job never walks the global fallback_providers chain: pinning buys route certainty and gives up outage fallback, while credential-pool rotation within one provider still applies to every job. The guide documents --pin/--unpin and user-requested pinned=true/false through cronjob_manage; an agent cannot choose a different model. Verify installed-version semantics and obtain approval before changing routing.

07

Run /new at natural boundaries on messaging platforms

The memory documentation now explains that the whole system is built around session end: MEMORY.md and USER.md carry essentials into the next session, and session_search fills the gaps once old context is gone. On messaging platforms where a chat is one continuous session surviving restarts, never resetting means compaction runs over an ever-longer history and the learning loop rarely fires. Run /new at finished tasks, topic changes, or the start of a day so memory pays off. Since v0.22.0 the idle/daily session_reset modes are retired, so /new or /reset is the only way to start fresh.

08

Recurring failures alert once; ack only what you mean

A cron job failing repeatedly with the same error pings once and then reminds on a cooldown, with a distinct incident per error signature; the guide says signatures ignore case, whitespace and measured durations such as 'idle for 603s', so a timeout that varies only in seconds stays one incident. A successful run resolves open incidents, while acknowledging one closes it for that exact signature only. Run `hermes cron doctor` for a read-only fleet health check and `hermes cron incidents` for durable failure records.

Memory tool: the replace action is gone; patch edits one span inside an entry, and every call needs an explicit target; shipped in v0.22.0

released · The memory guide (byte-identical on October 13 and 15) says the memory tool can add, patch, or remove entries. patch replaces only the old_text span inside the matched entry and keeps everything else; the span must occur once in that entry or the call is rejected and the agent retries with more surrounding text. To rewrite a whole entry, pass the whole entry as old_text (an exact whole-entry match wins over substring matches). The guide says there is no replace action: it overwrote the whole matched entry, and models used it as a find-and-swap, which wiped the other facts in multi-fact entries. A replace call now returns an error pointing at patch; writes staged for approval before the change still apply as staged. Every call also needs a top-level target of "memory" or "user", and a batch writes one store. Main-branch commit cf2ffb3 (October 13, 02:13 UTC) drops replace and cites 19 of 40 NVIDIA test tasks on Opus 4.8 where replace wiped sibling facts; 4125123 makes patch edit exactly one span; cb62ae4 requires explicit top-level targets; and 2c54533 (08:04 UTC) relaxes that so a nested target equal to the top-level one, or null, is accepted while a differing one is refused. On October 15 the GitHub compare API shows all four are ancestors of the v0.22.0 tag (and of v0.22.2), so this shipped in v0.22.0; v0.21.7 and earlier builds still have replace. Documentation and commit evidence; not tested locally.

There is no replace action. It overwrote the whole matched entry, and models used it as a find-and-swap, which wiped the other facts in multi-fact entries.
