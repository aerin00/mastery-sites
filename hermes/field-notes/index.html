02 / FIELDCRAFT

Small moves, sharper agent

Operational details that separate a demo from a dependable daily system.

01

Capture the successful procedure, not the whole transcript

Use /learn after a workflow has passed its acceptance check. Ask for a lean skill with prerequisites, pitfalls, and verification, placing longer material in reference files loaded on demand.

02

Keep memory compact and search history for detail

Keep durable conventions in bounded memory and use session_search for actual prior conversations. A promise to remember is not a persisted write: check the tool result, pending approvals, active profile and exact file. Memory snapshots refresh at a new session. For replace, old_text selects the whole entry; content must preserve all still-valid parts. /journey is a learning timeline, not an inventory of unused installed skills.

03

Give repository cron jobs an explicit workdir

The cron documentation says jobs are detached from repository context by default. Set an existing absolute workdir when approving a project job so its tools and project instructions resolve against the intended repository.

04

Check delivery separately from job execution

Verify an approved test at the intended destination; saved output is not delivered notification. The current cron guide documents a 60-second default standalone-send deadline and warns that a timed-out message may still arrive if already accepted. Read the destination receipt before retrying. Jobs created from request/response api_server sessions use a home-channel fallback for deliver: origin. These guide behaviors were not runtime-tested here.

05

Do not share one Hermes home between independent agents

The memory documentation warns that concurrent agents sharing a Hermes home can compound each other's automatic writes. Give independent agents separate profiles and verify the active scope before changing skills, memory, or scheduled jobs.

06

Make recurring inference selection deliberate

The current cron guide now says resolution is per-job pin, then cron.model/cron.model_provider, then the main model at fire time. This replaces the earlier creation-time snapshot/resnap advice: without either override, changing the main default retargets unpinned jobs. The guide documents --pin/--unpin and user-requested pinned=true/false through cronjob_manage; an agent cannot choose a different model. Verify installed-version semantics and obtain approval before changing routing. A session-only /model override should not be assumed to change the global default.

07

Run /new at natural boundaries on messaging platforms

The memory documentation now explains that the whole system is built around session end: MEMORY.md and USER.md carry essentials into the next session, and session_search fills the gaps once old context is gone. On messaging platforms where a chat is one continuous session surviving restarts, never resetting means compaction runs over an ever-longer history and the learning loop rarely fires. Run /new at finished tasks, topic changes, or the start of a day so memory pays off.

08

Recurring failures alert once; ack only what you mean

A cron job failing repeatedly with the same error pings once and then reminds on a cooldown, with a distinct incident per error signature. A successful run resolves open incidents, while acknowledging one closes it for that exact signature only. Run `hermes cron doctor` for a read-only fleet health check and `hermes cron incidents` for durable failure records.

Cron guide now says unpinned jobs follow the main model at fire time

documented-unverified · The retrieved guide replaces yesterday's creation-time snapshot and resnap guidance. Resolution is now documented as per-job pin, then cron.model/cron.model_provider, then the current main default. It adds --pin/--unpin and user-requested pinned=true/false on cronjob_manage, while prohibiting the agent from selecting a different model. This is a consequential correction to the prior edition, not a claim that an installed or tagged build has these semantics. The messaging guide separately says a chat /model override is session-scoped unless made global.

Change your main model and every unpinned job follows on its next run.

Before changing the main default, inspect installed-version behavior and effective job pins or cron defaults read-only. Keep routing changes user-approved; do not apply the superseded resnap advice blindly.

Memory guide clarifies save verification and whole-entry replacement

documented-unverified · New troubleshooting guidance distinguishes a textual promise from an actual memory tool write, staged approval from persistence, and one profile's memory from another's. It reiterates that a saved entry enters the system snapshot at the next session. The replacement section explicitly says old_text locates the whole entry and content replaces that entry, so a partial replacement can discard facts that were meant to survive. These are documentation clarifications, not runtime-tested findings.

must be the complete new entry, including every part of the old one you want to keep.

When a save appears missing, inspect the actual write result, pending approval and exact profile-local file. Preview complete replacement entries and verify the target after an approved write.

Cron can hold recurring jobs through a known provider quota-reset window

documented-unverified · The updated cron guide describes parking a recurring job when the subscription usage probe (currently OpenAI Codex) reports an exhausted limit with a retry-after duration and the entire fallback chain is unavailable. next_run_at moves to the first scheduled occurrence after quota_hold_until, avoiding repeated fires during that window. Mid-run model API 429s and one-shot jobs are excluded; any run that reaches the model clears the hold. This is documented behavior, not a local runtime test or a verified tagged capability.

One-shot jobs are not held.

When a recurring job appears delayed after quota exhaustion, inspect its hold and next-run state before retrying. Confirm installed-version support; do not change provider routing or production schedules to test this note.
