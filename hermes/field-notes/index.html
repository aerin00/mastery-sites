02 / FIELDCRAFT

Small moves, sharper agent

Operational details that separate a demo from a dependable daily system.

01

Capture the successful procedure, not the whole transcript

Use /learn after a workflow has passed its acceptance check. Ask for a lean skill with prerequisites, pitfalls, and verification, placing longer material in reference files loaded on demand.

02

Keep memory compact and search history for detail

Keep durable conventions in bounded memory and use session_search for actual prior conversations. A promise to remember is not a persisted write: check the tool result, pending approvals, active profile and exact file. Memory snapshots refresh at a new session. The memory guide now describes main-branch behavior with no replace action: patch swaps one unique span inside an entry and keeps the rest, and each call names its target store; v0.21.7 still has replace, which overwrites the whole matched entry. When memory is full, the guide now says the error states how many characters to free; retry as one operations batch that removes or shortens stale entries and adds the new one, since the limit is checked on the batch result. A staged write is pinned to the entry it targeted and is refused if that entry changed, so clear stale pending writes instead of approving them. /journey is a learning timeline, not an inventory of unused installed skills.

03

Give repository cron jobs an explicit workdir

The cron documentation says jobs are detached from repository context by default. Set an existing absolute workdir when approving a project job so its tools and project instructions resolve against the intended repository.

04

Check delivery separately from job execution

Verify an approved test at the intended destination; saved output is not delivered notification. The current cron guide documents a 60-second default standalone-send deadline and warns that a timed-out message may still arrive if already accepted. Read the destination receipt before retrying. Jobs created from request/response api_server sessions use a home-channel fallback for deliver: origin. These guide behaviors were not runtime-tested here.

05

Do not share one Hermes home between independent agents

The memory documentation warns that concurrent agents sharing a Hermes home can compound each other's automatic writes. Give independent agents separate profiles and verify the active scope before changing skills, memory, or scheduled jobs.

06

Make recurring inference selection deliberate

The current cron guide says resolution is per-job pin, then cron.model/cron.model_provider, then the main model at fire time, so without either override changing the main default retargets unpinned jobs. It now also says a pinned job never walks the global fallback_providers chain: pinning buys route certainty and gives up outage fallback, while credential-pool rotation within one provider still applies to every job. The guide documents --pin/--unpin and user-requested pinned=true/false through cronjob_manage; an agent cannot choose a different model. Verify installed-version semantics and obtain approval before changing routing.

07

Run /new at natural boundaries on messaging platforms

The memory documentation now explains that the whole system is built around session end: MEMORY.md and USER.md carry essentials into the next session, and session_search fills the gaps once old context is gone. On messaging platforms where a chat is one continuous session surviving restarts, never resetting means compaction runs over an ever-longer history and the learning loop rarely fires. Run /new at finished tasks, topic changes, or the start of a day so memory pays off.

08

Recurring failures alert once; ack only what you mean

A cron job failing repeatedly with the same error pings once and then reminds on a cooldown, with a distinct incident per error signature; the guide says signatures ignore case, whitespace and measured durations such as 'idle for 603s', so a timeout that varies only in seconds stays one incident. A successful run resolves open incidents, while acknowledging one closes it for that exact signature only. Run `hermes cron doctor` for a read-only fleet health check and `hermes cron incidents` for durable failure records.

Memory guide: the replace action is gone; patch edits one span inside an entry, and every call needs an explicit target (merged on main, not yet released)

merged-unreleased · The October 13 retrieval of the memory guide says the memory tool can add, patch, or remove entries. patch replaces only the old_text span inside the matched entry and keeps everything else; the span must occur once in that entry or the call is rejected and the agent retries with more surrounding text. To rewrite a whole entry, pass the whole entry as old_text (an exact whole-entry match wins over substring matches). The guide says there is no replace action: it overwrote the whole matched entry, and models used it as a find-and-swap, which wiped the other facts in multi-fact entries. A replace call now returns an error pointing at patch; writes staged for approval before the change still apply as staged. Every call also needs a top-level target of "memory" or "user", and a batch writes one store. Main-branch commit cf2ffb3 (October 13, 02:13 UTC) drops replace and cites 19 of 40 NVIDIA test tasks on Opus 4.8 where replace wiped sibling facts; 4125123 makes patch edit exactly one span; cb62ae4 requires explicit top-level targets; and 2c54533 (08:04 UTC) relaxes that so a nested target equal to the top-level one, or null, is accepted while a differing one is refused. The GitHub compare API shows all four ahead of v0.21.7, which is still the latest release, so stable-channel installs keep replace until the next tag. Documentation and commit evidence; not tested locally.

Skills guide: skills installed, created or removed mid-conversation are announced on your next message; shipped in v0.21.7

released · The October 10 retrieval of the skills guide adds 'Skills added during a conversation'. The skill list lives in the conversation's system prompt, which stays fixed so the provider's prompt cache keeps working. When a skill is installed, created or removed while a conversation is open (Skills Hub, hermes skills install in another terminal, a plugin, the curator, or the agent itself), the next message carries a short note naming new skills with their descriptions and the removed ones, sent once per change; the system prompt itself picks up the change at the next compaction. /reload-skills is not needed for this, though it still refreshes /skill-name slash commands. Main-branch commit 097fcaa (October 10, 02:31 UTC) explains that the earlier note only fired on the stored-prompt restore path, so long-lived classic CLI, TUI and Desktop agents never saw a mid-conversation change; the check now runs every turn, and a plugin install no longer announces its skills twice. On October 12 the GitHub compare API shows both are ancestors of the v0.21.7 tag, whose notes also name skills installed mid-session reaching the model without a prompt rebuild, so this shipped in v0.21.7. Memory guide: external-provider recall is kept whole by default, with spilling opt-in and a 100k-character ceiling; shipped in v0.21.7

released · The October 9 retrieval of the memory guide adds an 'External recall size' section. External memory providers now return their full prefetched context by default, up to a safety ceiling of 10x hooks.output_spill.max_chars (at least 100,000 characters). Recall above that ceiling still spills, so a runaway provider cannot overflow the context window. Setting memory.prefetch_spill_enabled: true opts a profile into replacing oversized recall with a head/tail preview and a file path. The guide warns that this can reduce replayed context, but the relevance-ranked middle is no longer immediately visible to the model, and it recommends using the provider's own recall budget where one exists. The opt-in uses the shared hooks.output_spill threshold, preview lengths and directory. hooks.output_spill.enabled: false still disables it, ordinary plugin hooks keep spilling by default, and settings are captured at provider registration, so Hermes must be restarted after a change. The guide's example config now shows prefetch_spill_enabled: false. Main-branch commits 2327290 ('make external prefetch spilling opt-in') and 8bff64d ('keep a runaway-recall ceiling when prefetch spilling is off', which says normal provider-budgeted recall of about 16 KB for Honcho is unaffected) were committed October 9 at 09:59 UTC. On October 12 the GitHub compare API shows both are ancestors of the v0.21.7 tag, so this shipped in v0.21.7. Not tested locally.

External memory providers return their full prefetched context by default

If a profile uses an external memory provider (Honcho, Hindsight, Mem0 and so on) and recall is replaced by a file-path preview, check whether the installed build predates v0.21.7 before changing config. After updating, prefer the provider's own recall budget over memory.prefetch_spill_enabled, and restart Hermes after changing either. Keep config changes user-approved.
