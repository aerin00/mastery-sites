02 / FIELDCRAFT

Small moves, sharper agent

Operational details that separate a demo from a dependable daily system.

01

Capture the successful procedure, not the whole transcript

Use /learn after a workflow has passed its acceptance check. Ask for a lean skill with prerequisites, pitfalls, and verification, placing longer material in reference files loaded on demand.

02

Keep memory compact and search history for detail

Keep durable conventions in bounded memory and use session_search for actual prior conversations. A promise to remember is not a persisted write: check the tool result, pending approvals, active profile and exact file. Memory snapshots refresh at a new session. Since v0.22.0 there is no replace action: patch swaps one unique span inside an entry and keeps the rest, and each call names its target store; builds before v0.22.0 still have replace, which overwrites the whole matched entry. Watch sessions.auto_prune across versions: v0.22.0 turned it on (deleting ended sessions inactive for 90 days at startup) and v0.22.3 moved it back to opt-in with a one-time prompt when disk runs low, so check the installed version's setting if session_search must reach older history. When memory is full, the guide now says the error states how many characters to free; retry as one operations batch that removes or shortens stale entries and adds the new one, since the limit is checked on the batch result. A staged write is pinned to the entry it targeted and is refused if that entry changed, so clear stale pending writes instead of approving them. /journey is a learning timeline, not an inventory of unused installed skills.

03

Give repository cron jobs an explicit workdir

The cron documentation says jobs are detached from repository context by default. Set an existing absolute workdir when approving a project job so its tools and project instructions resolve against the intended repository.

04

Check delivery separately from job execution

Verify an approved test at the intended destination; saved output is not delivered notification. The current cron guide documents a 60-second default standalone-send deadline and warns that a timed-out message may still arrive if already accepted. Read the destination receipt before retrying. Jobs created from request/response api_server sessions use a home-channel fallback for deliver: origin. These guide behaviors were not runtime-tested here.

05

Do not share one Hermes home between independent agents

The memory documentation warns that concurrent agents sharing a Hermes home can compound each other's automatic writes. Give independent agents separate profiles and verify the active scope before changing skills, memory, or scheduled jobs.

06

Make recurring inference selection deliberate

The current cron guide says resolution is per-job pin, then cron.model/cron.model_provider, then the main model at fire time, so without either override changing the main default retargets unpinned jobs. It now also says a pinned job never walks the global fallback_providers chain: pinning buys route certainty and gives up outage fallback, while credential-pool rotation within one provider still applies to every job. The guide documents --pin/--unpin and user-requested pinned=true/false through cronjob_manage; an agent cannot choose a different model. Verify installed-version semantics and obtain approval before changing routing.

07

Run /new at natural boundaries on messaging platforms

The memory documentation now explains that the whole system is built around session end: MEMORY.md and USER.md carry essentials into the next session, and session_search fills the gaps once old context is gone. On messaging platforms where a chat is one continuous session surviving restarts, never resetting means compaction runs over an ever-longer history and the learning loop rarely fires. Run /new at finished tasks, topic changes, or the start of a day so memory pays off. Since v0.22.0 the idle/daily session_reset modes are retired, so /new or /reset is the only way to start fresh.

08

Pin a job's timezone and its catch-up window

The cron guide now documents per-job timezone pinning (--timezone) and a catch-up window. A pinned job's expression is that zone's wall clock, so 0 9 * * * stays 09:00 across the zone's DST changes; --grace-minutes (0-1440) bounds how late a missed occurrence still runs, from the default of half the period clamped to 2 minutes-2 hours, and 0 means never catch up. These are documented behaviors, not runtime-tested here; verify against the installed version.

Cron guide adds per-job timezone pinning (--timezone) and a catch-up window (--grace-minutes), and clarifies manual-run semantics

documented-unverified · Retrieved October 29, the live cron guide gained a 'Per-job timezone' section: a job can pin its own zone (hermes cron create "0 9 * * 1-5" --timezone Asia/Hong_Kong), the expression is that zone's wall clock and stays at 09:00 across that zone's DST changes, an offset-less one-shot timestamp is read in the job's zone while an offset-carrying timestamp is already an instant, changing the zone recomputes next_run_at immediately, and an interval job has no wall clock so a pin has no effect; omitting it (or --timezone "" on edit) inherits the profile timezone. A 'Catch-up window' section says a missed occurrence is run late only inside a window of half the job's period clamped to 2 minutes-2 hours, with --grace-minutes (0-1440) overriding per job, 0 meaning never catch up, and no effect on once/interval schedules. The run-now text now says a manual run is an extra fire: the scheduled run still happens and the repeat count is not spent, so test-firing an 'in 30m' reminder keeps the real one. Documentation evidence retrieved from the live guide, not a local runtime test.

A missed cron occurrence is run late only inside a catch-up window: half the job's period, clamped to 2 minutes–2 hours.

If a recurring job should fire on a market's or reader's local clock, pin its zone instead of converting by hand, and set --grace-minutes deliberately (0 for exactness, a larger window for jobs that must not silently skip). Note that editing the zone moves the next fire immediately, and that a manual run no longer consumes the repeat count. Verify against the installed version before relying on either flag.

Cron now shipped in v0.22.3: agent runs keep their fire identity through restarts, Bot Chat delivery runs only inside the target profile's gateway, and hermes cron tick needs a running gateway

released · The October 16 cron guide adds an 'Admission recovery' section. An agent-backed run keeps its fire identity until output and a durable delivery handoff are recorded, and each tick reconciles unfinished receipts, including after an owner restart. A known terminal result is handed to delivery without running the agent again. A delivery interrupted after a send claim stays unknown and is not retried. An interrupted execution, or a prepared fire that cannot be found, stays paused for operator review and is never re-admitted or resumed automatically. hermes cron run exits nonzero for a known synchronous failure; a background dispatch is not a pass/fail verdict. Bot Chat delivery changes too. The 'Bot Chat delivery timeout' section (cron.bot_chat_delivery_timeout_seconds) becomes 'Bot Chat delivery completion': delivery is admitted to the target profile's running gateway and recorded as delivery_outcome=queued until the target's receipt settles, and a retry reuses the same receipt. If the target gateway is down, the run is recorded delivery_failed with no local fallback turn and no automatic redelivery; the old bot_chat_pending queue and the hermes chat -c "Bot Chat" lane are gone from the text. Also new: hermes cron tick runs one scheduler pass for an external crontab, but agent jobs execute only inside the gateway (skipped with a logged reason and not penalised while it is down); no_agent scripts still run; and --script must name a file, so --script "echo hi" is refused at creation. On October 21 the cron guide file on the v0.22.3 tag contains the 'Admission recovery' and 'Bot Chat delivery completion' sections and the file-only --script rule; the v0.22.2 tag still has the old timeout text. Related commits e2042c8 and 04e1447 (October 15), which key cron run history by scheduler admission, are ancestors of v0.22.3 per the GitHub compare API. Documentation and commit evidence, not tested locally.

If the target profile's gateway is not running, the run is recorded delivery_failed and no local fallback turn is run.

Before updating to v0.22.3, list any cron job that delivers to bot-chat and confirm the target profile's gateway will be running, because it will no longer queue or fall back. After an update or crash, check hermes cron list for jobs left paused instead of expecting them to resume, and rewrite any inline --script command as a file under the Hermes scripts directory.
