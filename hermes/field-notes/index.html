02 / FIELDCRAFT

Small moves, sharper agent

Operational details that separate a demo from a dependable daily system.

01

Capture the successful procedure, not the whole transcript

Use /learn after a workflow has passed its acceptance check. Ask for a lean skill with prerequisites, pitfalls, and verification, placing longer material in reference files loaded on demand.

02

Keep memory compact and search history for detail

Hermes memory is bounded and injected into the prompt; session_search retrieves actual stored conversations when specifics are needed. Keep durable preferences and conventions in memory rather than logs, transcripts, or temporary debugging state. The memory guide now clarifies that /journey shows skills with a creation or usage signal, not an inventory of all installed skills; unused bundled and hand-written skills stay off that timeline.

03

Give repository cron jobs an explicit workdir

The cron documentation says jobs are detached from repository context by default. Set an existing absolute workdir when approving a project job so its tools and project instructions resolve against the intended repository.

04

Check delivery separately from job execution

Specify the intended destination and verify an approved test reaches it; a saved output is not a delivered notification. The current cron guide distinguishes queued Bot Chat work from completion: unsupported live owners can defer never-started output, and the destination receipt is authoritative. Claimed or ambiguous attempts are not automatically replayed. Read the receipt before retrying; this guide behavior was not runtime-tested here.

05

Do not share one Hermes home between independent agents

The memory documentation warns that concurrent agents sharing a Hermes home can compound each other's automatic writes. Give independent agents separate profiles and verify the active scope before changing skills, memory, or scheduled jobs.

06

Make recurring inference selection deliberate

The cron guide describes per-job pins, then a cron-level default, then creation-time provider/model snapshots for otherwise unpinned jobs. `hermes cron resnap` refreshes an unpinned job's stored snapshot to the current global resolution; remaining unpinned does not mean later chat-model changes automatically retarget it. Per-job reasoning-effort pins also override the global and per-model defaults, and are not exposed on the agent's cron tool: model configuration stays a user decision. Verify installed-version behavior and obtain approval before changing inference routing.

07

Run /new at natural boundaries on messaging platforms

The memory documentation now explains that the whole system is built around session end: MEMORY.md and USER.md carry essentials into the next session, and session_search fills the gaps once old context is gone. On messaging platforms where a chat is one continuous session surviving restarts, never resetting means compaction runs over an ever-longer history and the learning loop rarely fires. Run /new at finished tasks, topic changes, or the start of a day so memory pays off.

08

Recurring failures alert once; ack only what you mean

A cron job failing repeatedly with the same error pings once and then reminds on a cooldown, with a distinct incident per error signature. A successful run resolves open incidents, while acknowledging one closes it for that exact signature only. Run `hermes cron doctor` for a read-only fleet health check and `hermes cron incidents` for durable failure records.

Failure incidents now alert once and remind on a cooldown, replacing per-run pings

documented-unverified · The cron guide's failure-incident section was rewritten: a recurring job failing with the same error now alerts once, with repeat pings withheld while the incident is alerted, and one reminder ping after failure_repeat_alert_hours (default 6) before silence. A different error mints its own incident and pings immediately; a successful run resolves open incidents and re-arms the signature; acknowledging closes the signature for good, reminders included. Related additions document per-job reasoning-effort pins, which override global and per-model defaults and are deliberately not exposed on the agent's cron tool. The retrieved guide also describes [CRON_FAILURE] as a strict first-line marker for the agent to declare a run failed when a delegated child or script it ran failed. These are documentation changes; publication date and tagged availability are unverified.

A recurring job that keeps failing with the same error alerts you once, not on every run.

Before adopting these behaviors, verify them on the installed build with an isolated test job: one ping on repeated identical failures, a reminder after the configured cooldown, and [CRON_FAILURE] marking a declared failure in `hermes cron runs` and `hermes cron incidents`. Do not modify production jobs or delivery targets merely to validate this note.

Cron scripts can receive a declared secret through the owning profile's env passthrough

documented-unverified · The cron guide now documents giving an authenticating script a credential the same way terminal and execute_code children get one: declare the variable name under terminal.env_passthrough in the owning profile's config.yaml and define the value in that profile's .env or an external secret source. The value resolves through the owning profile's secret scope, never the launch profile's process environment, and Hermes-managed provider credentials cannot be declared: the sanitizer rejects them. Script output logs presence (set/MISSING), never the value. This is documented behavior; publication date and tagged availability are unverified.

declare the variable name in the owning profile's config.yaml and define the value in that profile's .env

If an unattended script needs an external-service token, declare it through env_passthrough in the owning profile and store the value in that profile's own .env or secret source. Do not embed the value in the script, and confirm installed-version behavior before relying on the documented precedence.

A new max_input_tokens cap bounds background-review input replay cost

documented-unverified · The memory guide now documents auxiliary.background_review.max_input_tokens, which caps the SUM of replayed input tokens across a single review's provider requests; the loop stops before crossing it. Unset, the budget derives from the review model's resolved context window (75% of the window, capped at 600,000 tokens; a conservative 120,000-token fallback when the window cannot be resolved). The key lives under auxiliary:; a top-level background_review block is not read. This is documented behavior; publication date and tagged availability are unverified.

max_input_tokens caps the SUM of replayed input tokens for one review; the loop stops before crossing it.

Operators running the background review on expensive models can set auxiliary.background_review.max_input_tokens after checking installed-version support. Keep the key under auxiliary: and treat the documented fallback values as upstream claims, not measurements from this run.

Curator built-in pruning becomes opt-in; unused bundled skills are no longer silently archived

merged-unreleased · feat(curator)!: prune_builtins defaults to off, retrieved from main. The commit message reports bundled skills unused for 30 days were archived on a startup tick with no prompt (57 in one launch) and then suppressed from re-seeding on update, which reads as a broken install. Agent-created skills remain the curator's job; built-in pruning is now opt-in via curator.prune_builtins: true, and users already carrying that setting are unaffected. This is main-branch work after v0.21.3 with a committer timestamp; runtime behavior was not tested here.

If bundled skills appear to vanish from skills_list, check the installed curator behavior and the curator.prune_builtins setting; the fix is opt-in and not yet in a tagged release. Do not modify production skill stores to validate this note.
