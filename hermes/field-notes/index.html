02 / FIELDCRAFT

Small moves, sharper agent

Operational details that separate a demo from a dependable daily system.

01

Capture the successful procedure, not the whole transcript

Use /learn after a workflow has passed its acceptance check. Ask for a lean skill with prerequisites, pitfalls, and verification, placing longer material in reference files loaded on demand.

02

Keep memory compact and search history for detail

Keep durable conventions in bounded memory and use session_search for actual prior conversations. A promise to remember is not a persisted write: check the tool result, pending approvals, active profile and exact file. Memory snapshots refresh at a new session. For replace, old_text selects the whole entry; content must preserve all still-valid parts. When memory is full, the guide now says the error states how many characters to free; retry as one operations batch that removes or shortens stale entries and adds the new one, since the limit is checked on the batch result. A staged replace or remove is pinned to the entry it targeted and is refused if that entry changed, so clear stale pending writes instead of approving them. /journey is a learning timeline, not an inventory of unused installed skills.

03

Give repository cron jobs an explicit workdir

The cron documentation says jobs are detached from repository context by default. Set an existing absolute workdir when approving a project job so its tools and project instructions resolve against the intended repository.

04

Check delivery separately from job execution

Verify an approved test at the intended destination; saved output is not delivered notification. The current cron guide documents a 60-second default standalone-send deadline and warns that a timed-out message may still arrive if already accepted. Read the destination receipt before retrying. Jobs created from request/response api_server sessions use a home-channel fallback for deliver: origin. These guide behaviors were not runtime-tested here.

05

Do not share one Hermes home between independent agents

The memory documentation warns that concurrent agents sharing a Hermes home can compound each other's automatic writes. Give independent agents separate profiles and verify the active scope before changing skills, memory, or scheduled jobs.

06

Make recurring inference selection deliberate

The current cron guide says resolution is per-job pin, then cron.model/cron.model_provider, then the main model at fire time, so without either override changing the main default retargets unpinned jobs. It now also says a pinned job never walks the global fallback_providers chain: pinning buys route certainty and gives up outage fallback, while credential-pool rotation within one provider still applies to every job. The guide documents --pin/--unpin and user-requested pinned=true/false through cronjob_manage; an agent cannot choose a different model. Verify installed-version semantics and obtain approval before changing routing.

07

Run /new at natural boundaries on messaging platforms

The memory documentation now explains that the whole system is built around session end: MEMORY.md and USER.md carry essentials into the next session, and session_search fills the gaps once old context is gone. On messaging platforms where a chat is one continuous session surviving restarts, never resetting means compaction runs over an ever-longer history and the learning loop rarely fires. Run /new at finished tasks, topic changes, or the start of a day so memory pays off.

08

Recurring failures alert once; ack only what you mean

A cron job failing repeatedly with the same error pings once and then reminds on a cooldown, with a distinct incident per error signature; the guide says signatures ignore case, whitespace and measured durations such as 'idle for 603s', so a timeout that varies only in seconds stays one incident. A successful run resolves open incidents, while acknowledging one closes it for that exact signature only. Run `hermes cron doctor` for a read-only fleet health check and `hermes cron incidents` for durable failure records.

Skills guide: skills installed, created or removed mid-conversation are announced on your next message, without /reload-skills

merged-unreleased · The October 10 retrieval of the skills guide adds 'Skills added during a conversation'. The skill list lives in the conversation's system prompt, which stays fixed so the provider's prompt cache keeps working. When a skill is installed, created or removed while a conversation is open (Skills Hub, hermes skills install in another terminal, a plugin, the curator, or the agent itself), the next message carries a short note naming new skills with their descriptions and the removed ones, sent once per change; the system prompt itself picks up the change at the next compaction. /reload-skills is not needed for this, though it still refreshes /skill-name slash commands. Main-branch commit 097fcaa (October 10, 02:31 UTC) explains that the earlier note only fired on the stored-prompt restore path, so long-lived classic CLI, TUI and Desktop agents never saw a mid-conversation change; the check now runs every turn, and a plugin install no longer announces its skills twice. Separately, commit 18ee425 (October 9) makes hub installs download skill files from raw.githubusercontent.com pinned to the tree's commit, so an install costs about two API calls instead of one per file; the commit cites an anonymous install that used 143 calls and failed rate_limited. Through the GitHub compare API both are ahead of the v0.21.6 tag, so this is unreleased behavior. Not tested locally.

If anonymous hub installs hit GitHub rate limits on v0.21.6, setting a GitHub token remains the documented fix until this ships. Keep skill installs user-approved.

Memory guide: external-provider recall is kept whole by default, with spilling now opt-in and a 100k-character runaway ceiling

merged-unreleased · The October 9 retrieval of the memory guide adds an 'External recall size' section. External memory providers now return their full prefetched context by default, up to a safety ceiling of 10x hooks.output_spill.max_chars (at least 100,000 characters). Recall above that ceiling still spills, so a runaway provider cannot overflow the context window. Setting memory.prefetch_spill_enabled: true opts a profile into replacing oversized recall with a head/tail preview and a file path. The guide warns that this can reduce replayed context, but the relevance-ranked middle is no longer immediately visible to the model, and it recommends using the provider's own recall budget where one exists. The opt-in uses the shared hooks.output_spill threshold, preview lengths and directory. hooks.output_spill.enabled: false still disables it, ordinary plugin hooks keep spilling by default, and settings are captured at provider registration, so Hermes must be restarted after a change. The guide's example config now shows prefetch_spill_enabled: false. Main-branch commits 2327290 ('make external prefetch spilling opt-in') and 8bff64d ('keep a runaway-recall ceiling when prefetch spilling is off', which says normal provider-budgeted recall of about 16 KB for Honcho is unaffected) were committed October 9 at 09:59 UTC. Through the GitHub compare API, they are 300 commits ahead of the v0.21.6 tag, so the docs site describes unreleased behavior. Not tested locally.

External memory providers return their full prefetched context by default

If a profile uses an external memory provider (Honcho, Hindsight, Mem0 and so on) and you see recall replaced by a file-path preview, check whether your installed build predates these commits before changing config. After updating, prefer the provider's own recall budget over memory.prefetch_spill_enabled, and restart Hermes after changing either. Keep config changes user-approved.

Cron guide: an unwritable cron store now skips due runs, warns in four places and fires each job once on recovery

released · The October 8 retrieval of the cron guide adds 'Cron store not writable (full disk, read-only mount, permissions)'. When ~/.hermes/cron/ or a profile's cron/ directory cannot be written (ENOSPC, EROFS, EACCES), the scheduler does not run a job whose run it cannot record, to prevent double fires after recovery; the ticker keeps running and re-checks about once a minute. The outage shows in hermes cron status (leading with a 'NOT writable' warning, the OS error, last successful write and count of unfired due runs), a one-line banner in hermes cron list, hermes doctor (also warning under 100 MB free) and one gateway notice to the profile's home channels, plus the hermes.cron.store.writable and hermes.cron.store.skipped_runs gauges. No restart is needed: each job that stayed due fires once under normal misfire catch-up, not once per missed tick. The same retrieval says a silent live owner is reclaimed after max(3 x HERMES_CRON_TIMEOUT, script timeout, 2 h), with progress stamps keeping healthy long jobs alive. The v0.21.6 notes name the unwritable-store warnings, and the store docs commits (d85d23c, 33530d1) are ancestors of the tag. Not tested locally.

the scheduler does not run a job whose run it can't record. That prevents double fires after recovery.

If a scheduled briefing silently stops, run hermes cron status before editing jobs; a store warning points at disk space, mounts or ownership, not the job. Fix the filesystem rather than recreating jobs, then expect one catch-up fire per due job.

Memory guide: Honcho, Supermemory, Mem0 and now OpenViking leave the bundled set and install from the plugin catalog

released · The October 8 retrieval of the memory guide says Hermes ships 3 external memory provider plugins (Holographic, RetainDB and ByteRover), with Honcho, Hindsight, Supermemory, Mem0 and OpenViking available from the plugin catalog via hermes plugins install <name>. The October 6 text still listed OpenViking as bundled. Main-branch commit 05eecbc (October 7) removes the bundled OpenViking provider: it now ships from Volcengine's own repo through plugin-catalog/openviking.yaml, and the update-time memory migration installs the catalog plugin for homes configured for it. The commit warns that the catalog pin starts openviking-server with the full Hermes environment (the bundled copy filtered it) and suggests starting openviking-server yourself to avoid that. Earlier removals: Honcho (7e53b3e) and Supermemory (87be434) on October 2, Mem0 (781334e) on October 6, which keeps its provider name, mem0.json and MEM0_* keys. All four commits are ancestors of the v0.21.6 tag (818c13b), so these removals ship in that release. Documentation and commit evidence; not tested against an installed build.

Hermes ships with 3 external memory provider plugins — Holographic, RetainDB and ByteRover

Before updating a profile to v0.21.6, run hermes memory status on it. If it uses Mem0, Honcho, Supermemory or OpenViking, read the migration notice afterwards rather than assuming the provider carried over; for OpenViking, consider running openviking-server yourself so it does not inherit the full Hermes environment. Built-in MEMORY.md and USER.md are unaffected. Keep plugin installs user-approved.
