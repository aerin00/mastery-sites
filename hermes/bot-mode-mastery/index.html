SECTION 02HERMES / BOT MODE

The mental model shift

Old model

Chatbot

You→AI→Answer

You carry the routing, context switching, verification, and follow-up logic yourself.

Bot Mode model

Small operating team

You→Coordinator→Specialists→Coordinator→Outcome

The useful unit becomes Objective → roles → handoff → verification → decision → stop.

The upgrade: you increasingly stop saying “X do this, Coder do this, Default do this” and start saying “Default, own this outcome and use the team.”

SECTION 04HERMES / BOT MODE

The 5 core interaction patterns

1. Direct specialist request

Use when the right Bot is obvious and there is no orchestration problem.

@x-research

Investigate [QUESTION].

Focus on:
- evidence
- competing explanations
- what is actually new

Do not propose implementation.
Return your findings to the room.
2. Coordinator-owned delegation

Use when you know the outcome but not which specialist work is actually necessary.

@default

I want to determine whether [IDEA] is worth pursuing.

You are the decision owner.
Use the other Bots where useful.
Do not let this become a general brainstorm.

Return:
1. Decision
2. Evidence
3. Main risk
4. Smallest next action
3. Explicit cascade

Use when downstream work depends on upstream findings.

@default

Own this task:

[OBJECTIVE]

PHASE 1 — RESEARCH
Ask @x-research for external evidence that materially affects the decision.

PHASE 2 — DECISION
Evaluate the evidence. If the idea is not worth pursuing, stop.

PHASE 3 — FEASIBILITY
If it survives, ask @coder for the smallest technically valid experiment.

PHASE 4 — REVIEW
Check whether the experiment actually tests the original thesis.

PHASE 5 — FINAL
Return:
- Decision
- Evidence
- Proposed action
- Verification
- What would change the decision

Stop.
4. Bot-to-Bot dynamic follow-up

Use when the next specialist depends on what gets discovered.

@x-research

Investigate whether [TECHNOLOGY] appears mature enough for production use.

If a finding depends on technical feasibility,
mention @coder and ask it to evaluate that specific claim.

@coder:
Only respond to the technical questions X raises.

When the evidence and feasibility are complete, mention @default.

@default:
Synthesize the final recommendation.
5. Adversarial review loop

Use when you need disagreement, not division of labor.

@default

We are reviewing this proposal:

[PROPOSAL]

Assign:
- @x-research to challenge external assumptions
- @coder to challenge technical assumptions
- yourself to challenge scope and necessity

Each Bot should identify the single biggest weakness.
Respond to each other's objections.
Do not converge merely to reach agreement.

When disagreements are resolved or clearly identified,
give me the final decision.
SECTION 05HERMES / BOT MODE

Master prompts

Full work-session template

BOT MODE WORK SESSION

OBJECTIVE
[What outcome do I actually want?]

DECISION OWNER
@default owns the final result.

TEAM
Use specialist Bots only when their expertise materially helps.

OPERATING RULES
1. Do not have every Bot answer independently.
2. Delegate according to role.
3. If one Bot's answer creates a question for another specialist, @mention that specialist.
4. Specialists should challenge assumptions rather than simply agree.
5. Bots with nothing useful to add should pass.
6. Do not duplicate work another Bot already completed.
7. Complete prerequisite work before downstream work.
8. If new evidence invalidates the direction, stop the cascade.
9. Escalate to @user only for a real preference, authority decision, or missing requirement.
10. Do not expand scope beyond the objective.

FINAL OUTPUT
@default should finish with:

Decision:
Evidence:
Risks:
Next action:
Verification:

STOP CONDITION
Once the objective is resolved, stop.
Do not generate extra ideas, tasks, or projects unless asked.

Compact everyday template

@default

Own this outcome:

[OBJECTIVE]

Use @x-research for external evidence and @coder for technical feasibility or implementation when useful.

Delegate rather than having everyone answer independently.
Bots may @mention each other when a finding creates a question for another role.
Challenge assumptions, avoid duplicate work, and pass when there is nothing new to add.
Do prerequisite work before downstream work.
Escalate to @user only for a decision the team genuinely cannot make.

Finish with:
Decision
Why
Next action
Verification

Then stop.

SECTION 07HERMES / BOT MODE

Cascades, gates, and stop conditions

The highest-value Bot Mode workflows are not long conversations; they are controlled state transitions.

Research→Gate: worth it?→Feasibility→Gate: viable?→Implementation→Verification
Gates save work. A good cascade can terminate early with NO-GO. A bad cascade continues mechanically because “the next step” was already written.

Reusable gate template

@default

Investigate whether we should build [THING].

GATE 1 — EVIDENCE
Ask @x-research for evidence.
If evidence is weak, stop with NO-GO.

GATE 2 — FEASIBILITY
If evidence is strong, ask @coder whether a minimal implementation is feasible.
If feasibility is poor, stop with NO-GO.

Only if both gates pass should you recommend implementation.

For every gate:
- state PASS / FAIL
- state the evidence
- state why the next phase is or is not justified
SECTION 08HERMES / BOT MODE

Human escalation: use @user sparingly

Good escalation

  • Preference tradeoff only you can choose
  • Authorization for destructive/irreversible action
  • Missing requirement not inferable from evidence
  • Scope or risk acceptance decision

Bad escalation

  • “Python or PowerShell?” when the team can decide
  • Asking you to repeat evidence already available
  • Using questions to avoid technical judgment
  • Escalating every disagreement instead of resolving it
Do not ask me questions the team can resolve from evidence or expertise.

Escalate to @user only for:
- preference decisions
- authorization decisions
- destructive actions
- genuinely missing requirements

When escalating, ask exactly one decision question and stop.
SECTION 09HERMES / BOT MODE

How Hermes group chats work

Upstream Hermes docs Group rooms can contain 2–6 Bots. A user send can trigger up to three serial rounds. Mentioned Bots are scoped into the round; when nobody is mentioned, everyone may respond. Bots can reply or pass, and the room settles when a full round is silent. Upstream docs also describe hard caps of 10 messages per send and 3 rounds to prevent loops.

Bots can pull each other in with @name and can escalate real judgment calls with @user. Each member has its own persistent Group: <name> session.

BehaviorHow to use it
Not every Bot must speakTreat silence/pass as efficiency, not failure.
@mentions scope participationMention only the Bot whose role is needed now.
Bots can mention BotsUse this for dynamic follow-ups and cascades.
Rooms have bounded roundsGive a stop condition and let the room settle.
Persistent group sessionsKeep a room while the decision context remains the same.

Bot Chat vs Group Chat vs regular session / CLI

SurfaceBest forImportant behavior
Canonical Bot ChatLong-lived relationship with one Bot; bot-to-bot direct messagingUpstream Bot Mode treats this as a “forever chat.” message_agent is intended for canonical Bot Chats on Bot-Mode-managed installs.
Group ChatDeliberation, role handoffs, review, scoped @mentionsMembers keep their own group session; use room mentions rather than assuming canonical-DM tooling exists inside the group.

Do not confuse profile isolation with sandboxing. Hermes profiles isolate Hermes state (config, memory, sessions, skills, cron, credentials), but they do not automatically restrict filesystem access. Workspace and sandbox boundaries are separate concerns.
SECTION 11HERMES / BOT MODE

Interesting Hermes features to explore beyond basic Bot Mode

Profiles

A Bot is a profile

Upstream Hermes defines each profile as an independent Hermes home with its own config, API keys, memory, sessions, skills, cron jobs, state DB, and gateway state.

Why it matters: specialization is durable, not just a system prompt pasted into one conversation.

Routines

Give recurring work to the Bot that owns it

Bot Mode routines are backed by ordinary Hermes cron jobs. The result lands in that Bot’s own chat history, so recurring responsibility stays attached to the specialist.

Try: “X-Researcher owns a weekday signal brief; Default owns a weekly synthesis.”

Cross-machine Bot Mode

Rooms and Bots can span machines

Upstream docs describe group rooms that can seat Bots from multiple registered connections, with source-qualified handles such as @name-device.

Interesting future pattern: local Coder + remote GPU specialist + always-on research machine in one room.

Peer messaging

Bot-to-Bot DMs without the Desktop courier

Upstream Hermes supports gateway peers using API server URLs and keys, allowing machine-to-machine Bot DMs without a Desktop staying in the loop.

Use when: you eventually want always-on coordination across machines.

Export / distribution

Package a specialist as a reusable agent

Profiles can be exported/imported, and upstream docs describe profile distributions for versioned agent sharing while keeping credentials and memories machine-specific.

Idea: turn a polished X-Research role into a portable “research-bot” distribution.

Shared vs profile HOME

Hermes state isolation is not CLI identity isolation

On host installs, external CLI tools typically keep the real OS HOME. Upstream supports terminal.home_mode: profile for stricter per-profile CLI state.

Use only if needed: separate GitHub/SSH/cloud identities per Bot.

SECTION 12HERMES / BOT MODE

Hermes Kanban: when chat handoffs are no longer enough

Upstream Hermes docs Kanban is a durable SQLite-backed task board shared across Hermes profiles. It is meant for work that crosses agent boundaries, must survive restarts, needs human comments/review, may be retried, or needs a durable audit trail.

UsePrimitive
Short reasoning answer needed before parent continuesdelegate_task / conversational delegation
Live multi-Bot deliberation with you watchingBot Mode group chat
Persistent work queue, review states, retries, human-in-loop, discoverable historyKanban
Recurring responsibility over timeRoutines / cron
Useful maturity path:
Chat→Group delegation→Explicit cascades→Dynamic handoffs→Routines / Kanban
SECTION 13HERMES / BOT MODE

Anti-patterns

Everyone answers independently

Produces multiple mini-answers instead of a team result.

Fix: name a decision owner.

No prerequisite order

Coder starts designing before research changes the premise.

Fix: use phases and gates.

Forced participation

Every Bot repeats the same point.

Fix: explicitly allow passing.

Premature execution

Exploration turns into writes before a decision exists.

Fix: separate exploration room from execution step.

Over-escalating to you

The team asks questions it should resolve itself.

Fix: define escalation criteria.

No stop condition

The room keeps generating ideas after the objective is solved.

Fix: “Finish with X, then stop.”

Putting Scribe everywhere

Turns a durability specialist into another opinion generator.

Fix: capture the final synthesis downstream.

Assuming profile = sandbox

A role boundary in instructions is not a hard host boundary.

Fix: use scoped tools, cwd, and sandboxing separately.

High-value prompt library

Research → decision → implementation

Build Council
I want to explore this idea: [IDEA].

@x-research: investigate viability, similar approaches, and the biggest unknowns. Focus on evidence.

@default: after X responds, decide whether it is worth pursuing and define a small objective with success criteria.

@coder: only after Default defines the objective, propose the smallest experiment that could validate it. Do not build yet.

@default: finish with GO / NO-GO / NEEDS-MORE-EVIDENCE and one next action.

Grill this idea before I waste time

Adversarial
I’m considering building [IDEA].

@x-research: attack the external assumptions.
@coder: attack the implementation assumptions.
@default: attack the scope.

Agree on:
- strongest reason to build
- strongest reason not to
- cheapest decisive experiment

Do not give me a roadmap unless the idea survives.

Incident war room

Troubleshooting
INCIDENT ROOM

Symptom:
[ERROR / DESCRIPTION]

@default: maintain confirmed facts, hypotheses, and unchecked items.
@coder: diagnose locally; one hypothesis → one verification. No changes until understood.
@x-research: investigate upstream only if local evidence points to an external dependency or known bug.

Rules:
- no shotgun troubleshooting
- no destructive commands
- update diagnosis after each result
- stop when there is one justified next action

60-minute falsifiable experiment

Idea triage
I have a vague idea:

[IDEA]

@default: turn it into one falsifiable question.
@x-research: identify evidence that would raise or lower confidence.
@coder: design the smallest technical prototype needed to collect that evidence.
@default: synthesize a 60-minute experiment with a clear PASS / FAIL rule.

Do not turn it into a full project.

Architecture review board

Technical review
ARCHITECTURE REVIEW

Proposed change: [CHANGE]

@default: define intended outcome and boundaries.
@coder: assess complexity, coupling, rollback risk, tests, and smallest safe diff.
@x-research: check upstream patterns or alternatives when relevant.

Return exactly:
KEEP AS PROPOSED
REVISE
or REJECT

If REVISE, give the minimal revision.

Signals, not interesting links

Research
@x-research: research [TOPIC] and bring back only developments that materially change what I should believe, build, watch, or investigate.

For each finding include evidence and why it matters.

@default: reject anything merely interesting but not decision-relevant.

Finish with:
- 3 signals worth keeping
- 1 thing to investigate deeper
- 1 thing to ignore

CEO / Researcher / Engineer decision room

General purpose
DECISION ROOM

Decision: [QUESTION]

@default: act as decision owner. Define criteria.
@x-research: act as evidence lead. Challenge assumptions.
@coder: act as feasibility lead. Evaluate constraints and reversibility.

Disagree when warranted rather than converging for politeness.

@default finishes with:
Decision
Why
What would change the decision
Next smallest action
