Quick answer

The three naming questions

Documented

SKILL.md

Yes. Each file-based skill uses one singular SKILL.md inside its own folder. There is no standard plural SKILLS.md.

User convention

TEAMS.md

Useful as a shared roster, but not documented as a reserved Grok Bot file. A coordinator may create it to track roles and handoffs.

Documented

AGENTS.md

Recognized by Cursor agents in coding projects. It is not the documented global operating manual for ordinary Grok Bot work.

Most important correction: your Bots share one persistent cloud computer. They have separate screens and separate learned memories, but share files, browser sessions, command-line credentials, and installed plugins.

Unverified Grok Bot may generate TEAMS.md during a particular onboarding or coordinator workflow, but current official documentation does not assign special automatic behavior to that filename.

Files & conventions

A practical shared workspace

These files are an operating convention, not a claim that Grok Bot automatically loads every filename. Put an instruction in the coordinator's profile telling it which files to read.

Suggested folder structure
/workspace/agent-system/
├── TEAMS.md                 # roster, responsibilities, handoff rules
├── OPERATING_RULES.md       # shared safety and evidence rules
├── PROJECTS.md              # active projects and current owners
├── DECISIONS.md             # consequential human decisions
├── projects/
│   └── project-name/
│       ├── BRIEF.md         # outcome, scope, sources, acceptance checks

Decision guide

Should this be a Bot, skill, routine, or group?

Does the work need a durable owner, separate memory, tools, or approval boundary?
Create a focused Bot.
Is it one reusable procedure that an existing Bot can perform?
Create a skill.
Has the procedure worked safely and repeatedly with a stable trigger?
Add a routine.
Do several existing Bots need one outcome and visible handoffs?
Create a group chat.
Is it a temporary, bounded, independent task?
Use a temporary worker or Cloud Agent.
Is the proposed Bot merely a new format, schedule, audience, or prompt?
Keep the existing Bot; use a skill or routine.
Best default: improve an existing Bot, add a skill, prove it manually, then consider a routine. New persistent Bots should be the last step, not the first.

Recommended setup

A five-Bot research team

This structure fits your source-heavy work, including financial-astrology claims, technical research, Copilot documentation, and knowledge-base design.

CoordinatorDefines the finish line, assigns one owner per stage, tracks blockers, and assembles the reviewed result.
Source ResearcherFinds and consumes authoritative sources. Preserves links, dates, and exact supporting passages.
Claim ExtractorTurns sources into discrete claims, conditions, variables, exceptions, and testable rules.
Skeptical ReviewerIndependently opens sources and checks provenance, contradictions, freshness, and overreach.
PublisherProduces the final readable report, HTML, spreadsheet, or document using only reviewed material.
Keep research and verification separate. The Reviewer should inspect the sources independently, not merely review the Researcher's summary.

Paste-ready template

Coordinator Bot description

Put durable rules in the Bot description. Keep project-specific assignments in messages.

Coordinator profile
You are my Bot Coordinator.

Your job is to understand the requested outcome, choose the smallest suitable
team, give each stage one clear owner, monitor progress, resolve handoffs, and
return one integrated result.

At the start of a project:
1. Read /workspace/agent-system/TEAMS.md.
2. Define the deliverable, authoritative sources, constraints, acceptance
   checks, approval stops, deadline, and unresolved questions.
3. Reuse existing Bots and skills first.
4. Create no Bot, group, skill, routine, connection, or external write without
   my explicit approval.

Delegation:
- Give every handoff the objective, inputs, constraints, expected output,
  validation check, and approval boundary.
- Parallelize only independent workstreams.
- Never send the same task to multiple Bots unless I request independent review.
- Use one owner per stage.
- Require the Reviewer to work from original sources.
- Do not recursively create more coordinators.

Status:
- Maintain the project ledger.
- Record owner, stage, deliverable, sources, blocker, next action, and update time.
- Stay quiet when nothing materially changed.
- Contact me only for a decision, approval, blocker, material risk, or result.

Safety:
- Never send, publish, purchase, delete, change permissions, expose confidential
  information, or modify production without explicit approval.
- Separate verified facts, inferences, unresolved items, completed actions, and
  proposed actions.

Paste-ready template

Research group kickoff

Use a group when the Bots need one shared outcome and visible handoffs. Use direct messages when only the next owner needs the result.

Group-chat kickoff
We are producing one source-grounded research brief.

@Source Researcher
Find the authoritative and relevant sources. Record title, author, publication
date, event date, URL, and the exact claim supported. Consume the actual source,
not only search-result summaries.

@Claim Extractor
Turn the evidence into discrete claims. Preserve exact numbers, dates,
conditions, exceptions, and uncertainty. Separate source statements from your
inferences.

@Skeptical Reviewer
Independently open the sources and check every material claim. Identify missing
evidence, contradictions, outdated information, circular sourcing, and claims
broader than the evidence supports.

@Publisher
Wait for the review. Produce the final brief using only supported claims. Keep
disputes and unresolved questions visible.

@Coordinator
Own routing, status, blocked work, acceptance checks, and final assembly. Do not
duplicate specialist work.

Do not publish or contact anyone. A stage is complete only when its artifact,
source trail, and unresolved issues are available for review.

Emerging practices

Tips worth trying

One project, one group, one rosterSeparate projects to control noise. Reuse existing specialists and keep the group small.
Use a visible task ledgerTrack task, owner, stage, sources, deliverable, blocker, next action, and update time outside chat.
Keep changing facts out of memoryPut current projects, deadlines, and source status in files or a board. Use memory for stable preferences.
Teach, then hardenA screen recording captures clicks, not judgment. Add decision rules, failure handling, validation, and approval stops.
Parallelize independent branches onlySplit by source set or research question. Do not ask several Bots to perform the same stage unless testing agreement.
Log every handoffRecord who sent what, supporting sources, acceptance check, and whether the next Bot accepted or rejected it.
Make silence the defaultTell Bots to report only material changes, blockers, approvals, and completed results.
Prepare before executingLet early routines gather, reconcile, draft, and recommend. Keep external actions behind human approval.
Cap spawning depthLet the coordinator call existing Bots and temporary workers, but do not allow coordinators to create coordinators.
Require reviewable evidenceAsk for direct source links, dates, action logs, validation results, and an explicit list of anything not verified.
Audit the roster weeklyFind duplicate Bots, overlapping skills, unused routines, noisy notifications, and missing human owners.
Revise the same artifactAsk Bots to improve an existing deliverable instead of producing disconnected copies with competing truth.

Common failure modes

FailureWhat it looks likeControl
Bot zooMany narrow Bots with overlapping jobs and unclear ownership.Require a durable responsibility before creating a Bot.
Memory dumpEvery fact gets saved, including stale project status.Use memory only for stable context; use source files for changing facts.
Coordinator bottleneckThe manager repeats specialist work or rewrites every result.Coordinator routes and checks completion; specialists own the work.
Duplicate parallel workSeveral Bots answer the same question and create noise.Assign one owner per stage and split only independent branches.
Polished wrong answerThe Publisher hides unsupported claims in a fluent report.Require independent source review before publication.
Brittle recorded skillA website changes and the Bot clicks the wrong nearby control.Add outcome checks, failure states, and a safe test before scheduling.
Invisible failureThe final output is wrong but nobody knows which handoff broke.Maintain a task and handoff ledger with validation results.
Recursive spawningManagers create more managers and usage grows without clearer output.Cap delegation depth and require approval for persistent Bot creation.

Safety

Boundaries that should remain human

Bots can do preparation autonomously. Consequential actions should stop at an explicit review point.

Usually safe to prepare

Research, reconcile, classify, draft, summarize, propose, create a review list, or assemble evidence.

Require approval

Send, publish, purchase, delete, change permissions, expose confidential data, modify production, or make commitments.

Verify before approving

Show the exact target, current state, proposed change, expected effect, sources, and reversal plan when relevant.

For BC Hydro work: do not connect internal systems, upload protected material, or let Grok Bot act inside corporate services unless the platform and exact workflow have been approved under your organization's security and AI-governance rules.
