What you can build without leaving the SharePoint boundary

A working catalogue of every automation and Copilot capability available under a partially federated Power Platform model, sorted by whether you can build it today, must clear it with an IT Advisor first, or cannot build it at all.

The governing rule

Citizen development on Power Platform is not permitted, with one exception: Power Apps and Power Automate flows created directly from a SharePoint Online list or library, through the Integrate or Workflows menus, where the solution interacts only with SharePoint lists and libraries.

What that leaves you

  • The whole SharePoint no-code layer: Rules, column and view JSON formatting, content approval, versioning, retention labels, content types, and document sets.
  • Power Automate flows built from a list or library that use only the SharePoint connector.
  • Power Apps list-form customisation through Integrate > Power Apps > Customize forms.
  • Microsoft 365 Copilot across Word, Excel, PowerPoint, Outlook and SharePoint, plus SharePoint agents grounded on your own site.
  • Client-side Office automation that never touches Power Platform: Excel Power Query, Office Scripts run manually, Word mail merge.

The one question that decides most of your builds

Almost every useful flow needs to notify somebody, which pulls in Office 365 Outlook, Approvals, Teams or Office 365 Users. These are Standard, licence-included connectors that never touch Dataverse, SQL or an API, but they are not SharePoint. Section C sets out the ambiguity and the IT Advisor questions give you the exact wording to put to them.

B. Power Automate flows created from a SharePoint list or library

The SharePoint connector is Standard and licence-included. A flow that starts from a list and uses only this connector is squarely inside the boundary.

Triggers available

When an item is created, When an item is created or modified, When an item or a file is modified, When an item is deleted, When a file is created (properties only), and the manual triggers For a selected item and For a selected file.

C. Adjacent Standard connectors

This is the crux of the governance ambiguity. Every connector below is Standard and included in your licence, and none touches Dataverse, SQL or an API. But on a literal reading of "interacts only with SharePoint lists and libraries", they are arguably out of scope.

Two readings, one answer needed. On a licensing reading these are all fine. On a data-scope reading they are not SharePoint. A reasonable ruling is that they are in scope, but do not assume it. The IT Advisor questions below have the wording to put to them.

D. Power Apps from a SharePoint list

Form customisation is the single sanctioned Power Apps exception. The menu item next to it is not.

Read the menu carefully. Integrate > Power Apps > Customize forms is permitted. Integrate > Power Apps > Create an app builds a standalone canvas app and is outside the boundary. Do not use it.

Customize forms

Permitted

Opens the list form in Power Apps Studio with a SharePointIntegration control exposing OnNew, OnEdit, OnView, OnSave and OnCancel.

What you can achieve

  • Change control types, for example a dropdown to radio buttons or a rating control.
  • Conditional show and hide driven by formulas.
  • Field-level validation beyond what list validation offers.
  • Multi-column layouts, tabs and sections.
  • RequestHide() to close the form panel programmatically.

Limits

  • Generic lists and libraries only. Announcements, Contacts and Tasks templates are unsupported.
  • On a document library it edits metadata only, never the file itself.
  • The form cannot exist outside the list and cannot hide the surrounding SharePoint chrome.
  • It does not scale responsively for mobile the way a standalone canvas app does.
  • No proper application lifecycle management.
  • Stays in boundary only while you add no other data source.

Grounding a SharePoint agent well

  • Keep individual SharePoint files to a maximum of roughly 36,000 characters, about 15 to 20 pages, for reliable retrieval.
  • When you specify up to 20 files, Copilot searches the full contents of all of them.
  • Ground the agent on a single controlled library rather than a whole site where precision matters.
  • Keep it read-only. That is both the safest posture and the clearest in-boundary claim.

Worked patterns

Six end-to-end designs built to stay inside the boundary, with every gray-area step flagged so it can be removed if ruled out.

1. Request intake to approval to archived record

Permitted core

A SharePoint list with a customised form via Customize forms handles intake. A flow on When an item is created sets status and calls the SharePoint connector's Create an approval request for an item or file. On approval, Update item sets the status and Move file archives the record to a library carrying a retention label.

Confirm first Notifications through Office 365 Outlook, and richer multi-stage routing through the Approvals connector, are the gray-area steps. Keep them in a single isolated branch.

2. Recurring quarterly collection replacing an emailed workbook

Permitted core

Replace the workbook with a SharePoint list, one row per line item, with the quarter as a column. A scheduled recurrence flow using only the SharePoint connector opens the collection window and flips a status column. Contributors edit directly in the list. A SharePoint page with a list web part becomes the live view, and Excel Power Query or Copilot in Excel reads the list for analysis.

Confirm first Reminder emails to contributors.

3. Reconciliation of two lists with variance flagging

Fully permitted

An inventory list and a billing list. A flow runs Get items against both, matches on a key, and writes variances to a reconciliation list. A Variance column with JSON column formatting shows red and green at a glance. This pattern is entirely SharePoint-scoped provided you avoid the Excel and Outlook connectors.

Confirm first An emailed summary of the variance run, if permitted.

4. Controlled document library with an agent

Fully permitted

A library with content types, content approval enabled, and a default retention label, plus a read-only SharePoint agent grounded on that library. Up to 20 source items, documents rather than Lists. This is the canonical in-boundary knowledge base pattern and needs no review.

5. Reminder and escalation on overdue items

Permitted variant available

A scheduled flow queries the list for items past due, using an indexed date column to stay under the view threshold. The fully in-boundary variant writes an Escalated flag and relies on a Rule or a filtered view to surface it, avoiding Outlook entirely.

Confirm first Emailing the owner, then the manager after a set number of days, which requires Office 365 Users to resolve the manager.

6. Recurring status page or news post

Fully permitted

Copilot in SharePoint drafts a status page or news post from a prompt, or a flow uses Create file and page provisioning to publish a recurring status page from list data. Copilot authoring is covered by the Copilot licence, and flow-based page creation stays within the SharePoint connector.

Coordinator workflow, mapped

The invoice-to-closeout coordinator process placed onto the permitted stack, stage by stage. Three of the source guide's eight automation opportunities sit outside the boundary as written, and one cannot work at all for a reason unrelated to governance.

Where the source guide's own evidence lives. The references in the coordinator guide follow the pattern bchydro.sharepoint.com/:fl:/r/contentstorage/.../CopilotNotebooks/..._nb/<name>.page, ending in p=%40fluidx%2Floop-page-container. Those are Copilot Pages inside a Copilot Notebook, held in a SharePoint Embedded container: not visible in the SharePoint admin center site list, bound to one user's identity, with no library, no inherited permissions and no navigation. Three corrections to the source roadmap

1. The aging dashboard does not need Power BI

Permitted substitute

The guide proposes SharePoint plus Power BI. Power BI is a separate licensed service outside the boundary, and its scheduled refresh against SharePoint lists is historically unreliable. Build it natively instead:

  • A number column Days Outstanding written by a nightly scheduled flow. It cannot be a calculated column: SharePoint calculated columns do not support volatile functions such as TODAY(), and they recompute only when the item is saved. See build procedure 5.
  • A choice column Aging Bucket with values <30, 30-60, 60-90, >90.
  • JSON view formatting to colour the bucket, and a view grouped by bucket, surfaced on the site page as a list web part.

Same dashboard, inside the boundary, with no licensing conversation.

2. Intake should be a Lists form, not Microsoft Forms

Removes a gray-area dependency

"SharePoint Request Form" is ambiguous in the guide, and the two readings differ sharply. Microsoft Forms plus a routing flow uses the Microsoft Forms connector, inherits the section C ambiguity, and creates a second store of truth. A Microsoft Lists form is a shareable link that writes straight into the list: no connector, no flow, no gray area.

Use the Lists form and send IMs the link. The only reasons to prefer Forms would be anonymous responses or branching logic, and neither applies here.

3. Copilot-generated project summaries will not work as described

Blocked, not by governance

Native SharePoint agents cannot use Lists as a knowledge source. They ground on sites, pages and document libraries only. An agent therefore cannot answer "has the customer paid on this WBS" from the tracking list, however well the list is built.

Three ways around it, in order of preference:

  • Generate a recurring status page. A scheduled flow writes current list data into a SharePoint page. The agent reads pages. This gives IMs a Copilot-answerable surface without exposing the list.
  • Copilot Chat with the list open. Works for you, ad hoc, not for a self-serve IM.
  • Export a status workbook to the library. Uses Excel Online (Business), so this one is a gray-area step.

Do not build the agent expecting to point it at the list. It will ground on nothing and answer confidently anyway.

SAP FPL9 is a permanent wall

No connector to SAP exists inside the boundary, and no IT Advisor ruling will create one. Payment status will be entered by a person indefinitely. What automation can remove is the deciding, not the checking:

  • A Next Follow-Up Date column written by a flow from the invoice date and payment status.
  • A view filtered to Next Follow-Up Date <= today and Payment Status <> Paid. That view is the day's FPL9 worklist, generated rather than remembered.
  • After the check, the coordinator updates two fields and the flow recalculates the next follow-up date.

The person still opens SAP. They no longer decide what to open, and nothing falls through because someone was on leave.

Revised roadmap, sequenced by boundary dependency

Permitted

One list with the twenty columns, one document library, Lists form intake, Customize forms for the requisition screen, JSON formatting for status and aging, the calculated Ready for Closeout field, and the six reconciliation checklist columns. Retention label on the library. This is most of the value and none of the governance risk.

Phase 2, after the section C ruling

Flows for approval routing, status movement, Sundry Billing follow-up flags and payment reminder scheduling. Design each with the notification step in a single isolated branch so it can be removed cleanly.

Phase 3, once the list is populated

Permitted

A recurring status page generated from list data, then the SharePoint agent grounded on that page and the document library. Not before: an agent grounded on an empty library is worse than no agent.

Not on the roadmap. Power BI, Planner Premium, and anything reaching SAP.

Build procedures

Twelve step-by-step procedures covering everything in the permitted stack, in build order. Every one of these can be executed today without an IT Advisor ruling. Where a step would cross into the gray area it is labelled and isolated.

Build order matters. Procedures 1 to 4 establish the record and must come first. Procedures 5 to 8 add automation over a list that already has data in it. Procedures 9 to 12 are independent of the others and can run in parallel.

1. Provision the tracking list

Procedure 1

Permitted

Prerequisite: the site exists and you hold Full Control or Edit on it.

Site contents  >  New  >  List  >  Blank list
+ Add column  >  See all column types

Do not use Import from Excel. Columns brought in from a spreadsheet default to basic text and number types and cannot afterwards be changed to Person or Lookup. Build the columns by hand.

Column set. Intake fields: Request Type (Choice), Customer (Text), Project / WBS (Text), Amount (Currency), IM / Requestor (Person), Billing reason (Multi-line), PO / Reference (Text). Process fields: Status (Choice), Financial Coordinator Owner (Person), IM Approval Status (Choice), Sundry Billing Submitted Date (Date), Invoice Number (Text), Invoice Date (Date), Payment Status (Choice), Payment Received Date (Date), Last FPL9 Check Date (Date), Next Follow-Up Date (Date), Days Outstanding (Number), Aging Bucket (Choice), Reconciliation Status (Choice), Finance Approval Status (Choice), Closeout Date (Date), Notes (Multi-line, append-only). Reconciliation checklist: six Yes/No columns.

Index before you have data.

Settings (gear)  >  List settings  >  Indexed columns  >  Create a new index
  Index: Status, Invoice Date, Payment Status, Next Follow-Up Date

Defaults. Set Status default to New and IM Approval Status default to Pending in each column's settings, so form submissions arrive workflow-ready.

Views. Create the filtered views now, not later. Every view must be capable of returning fewer than 5,000 items. Automatic index creation only happens below 20,000 items; above that the index is built in the background.

2. Create the intake form

Procedure 2

Permitted

Prerequisites. Two, and both will stop you cold if unmet.

  • Site sharing. The Forms option is not visible if the sharing level "People in organization with the link" is disabled on the site collection. No Forms button means this setting, not a missing licence. It requires a site administrator.
  • Internal respondents only. Custom forms support only "People in organization with the link can respond," and guest accounts in the tenant are not authorised. An external respondent sees "This link is only available to internal users," and no setting changes that.
Open the list  >  command bar  >  Forms  >  + New form
  toggle off every column respondents should not see
  drag to reorder, mark required fields
  Add new field       (creates a new column on the list)
  Settings (gear)     (theme, logo, Accept responses toggle)
  Send form  >  Copy link

Clicking Copy link is not optional. To share to all internal accounts the creator must click Copy link at least once. Until then, colleagues get a permission error even though the form exists. This is behind most "some users can access it, some cannot" reports.

Permission model. "People in organization with the link can respond" is a new permission for lists. Respondents can open the form but cannot read or edit the list's content, and the permission is removable through Manage Access. That is the whole reason to prefer this over granting Contribute on the list, which would expose every other row.

Authoring rights. Anyone with Edit permission can customise the form. Drop a group to Contribute to hide the option from them if you do not want IMs redesigning your intake.

Fields to expose. Required: Request Type, Customer, Project / WBS, Amount, IM / Requestor, Billing reason. Optional: PO / Reference, Attachments. Toggle every process field off.

Branching trap. Conditional branching reached general availability in November 2024 and shows or hides questions based on earlier answers. It applies to the form, not the list. If a column is required on the list and branching skips it, the row lands and is then flagged as incomplete. Enforce required-ness on the form, never on the list column, wherever branching can skip that field. If the branching control is absent, click a question, then the "..." menu, then Add branching before assuming the feature is off.
Unsupported column types. Managed Metadata and Average Rating cannot appear on a Lists form. Text, Choice, Date and Time, Multi-line, Person, Number, Yes/No, Hyperlink, Currency, Location, Image, Lookup and Attachments all work.

Limits. Formatted output has a display limit of roughly 1,000 characters and does not render in grid edit view. Keep nested conditions shallow: performance degrades with deeply nested logic on large views.

4. Compute closeout readiness

Procedure 4

Permitted
+ Add column  >  More...  >  Calculated (calculation based on other columns)
  Return type: Single line of text

=IF(AND([Cost Report Received],[Invoice Issued],[Payment Received],
        [Variance Resolved],[Documentation Complete],[IM Signoff]),
    "Ready","Not ready")

What calculated columns cannot do. They do not support volatile functions such as TODAY() or ME(), and they recompute only when the item is saved, never on a schedule. Anything time-dependent must be written by a flow. That is why Days Outstanding is a plain number column filled by procedure 5, not a calculated column.

5. Nightly aging flow

Procedure 5

Permitted SharePoint connector only
List  >  Automate  >  Power Automate  >  Create a flow  >  Scheduled cloud flow
  Recurrence: Day, 1, at 05:00 local

Action Get items, with a filter tight enough to stay well inside the request ceiling:

Filter Query:  PaymentStatus ne 'Paid' and InvoiceDate ne null
Top Count:     500

Then Apply to each with a single Update item, setting Days Outstanding to:

div(sub(ticks(utcNow()), ticks(item()?['InvoiceDate'])), 864000000000)

And Aging Bucket to:

if(greater(div(sub(ticks(utcNow()), ticks(item()?['InvoiceDate'])), 864000000000), 90), 'Over 90',
if(greater(div(sub(ticks(utcNow()), ticks(item()?['InvoiceDate'])), 864000000000), 60), '60 to 90',
if(greater(div(sub(ticks(utcNow()), ticks(item()?['InvoiceDate'])), 864000000000), 30), '30 to 60', 'Under 30')))

Request budget. Every Update item is a request against the 6,000 per 24 hours Standard ceiling. Five hundred open items nightly consumes roughly 500 requests plus overhead. Sustained overage for 14 days disables the flow.

The same pattern writes Next Follow-Up Date, which drives the FPL9 worklist view.

6. Create a Rule

Procedure 6

Permitted not Power Automate
List  >  Automate  >  Rules  >  Create a rule
  When:  a column changes  /  an item is created  /  an item is deleted
  Then:  notify someone

Reach for this before a flow. A Rule is a native list feature with nothing to maintain, no run history and no request budget.

Limits. Notify, and in libraries move or copy, are the only actions. No digests. The email format is not customisable. You need Edit or Contribute to create one. Rules are unavailable on Site Pages libraries, and multi-line text columns cannot act as a trigger.

7. Approval flow using the SharePoint connector

Procedure 7

Permitted with one isolated gray-area branch
List  >  Automate  >  Power Automate  >  Create a flow
  Trigger:  When an item is created or modified
  Condition: Status is equal to 'Ready for Approval'
  Action:   Create an approval request for an item or file   [SharePoint connector]
  Action:   Update item  ->  IM Approval Status, approval date, approver

Use the SharePoint connector's own approval action rather than the separate Approvals connector wherever the approval shape allows. It surfaces in the list and keeps the flow entirely inside the boundary.

Isolate anything that is not SharePoint. If you add an Office 365 Outlook notification, put it in a single scope named GRAY-AREA notification containing nothing else, so the whole scope can be deleted in one action if the IT Advisor rules Standard connectors out of scope.

Supported templates. Flows for lists work only on generic lists (template 100) and generic libraries (template 101). Standard Get items and Update item handle a maximum of 12 lookup columns and cannot write Image columns.

8. Customise the list form with Power Apps

Procedure 8

Permitted the sanctioned exception
List  >  Integrate  >  Power Apps  >  Customize forms
Not the menu item below it. Integrate > Power Apps > Create an app builds a standalone canvas app and is outside the boundary.

The form opens in Power Apps Studio with a SharePointIntegration control exposing OnNew, OnEdit, OnView, OnSave and OnCancel. Use RequestHide() to close the panel programmatically.

File  >  Save  >  Publish to SharePoint

The one rule that keeps it in boundary: add no second data source. The moment the form connects to anything other than its own list, it leaves the exception. Note also that unlike a Lists form, a customised form requires the user to have access to the list.

Limits. Generic lists and libraries only. On a library it edits metadata only, never the file. It cannot exist outside the list, cannot hide the SharePoint chrome, does not scale responsively for mobile, and has no proper lifecycle management.

Retention. Labels are authored in Microsoft Purview and published to the site, then applied as a library default through library settings. Publication can take up to seven days to reach a site, so do this early. Manual labelling works on E3; auto-apply needs E5, E5 Compliance or an add-on.

Enable Document Sets as a site collection feature first if you want a closeout package to behave as one governed unit with shared metadata.

10. Create the read-only SharePoint agent

Procedure 10

Permitted Copilot licence, not Power Platform
Document library  >  Copilot  >  Create an agent
  Add sources     (maximum 20 items: sites, libraries, folders, files)
  Set behaviour   (read-only: answer from these sources, do not act)
  Save            (lands as a .agent file in Site Assets > Copilots)
  Share           (with the group who need to query it)

The hard limit that shapes the design. Native SharePoint agents cannot use Lists as a knowledge source. They ground on sites, pages and document libraries only. To make list data answerable, generate a recurring status page from the list with a scheduled flow and add that page as a source.

Grounding quality. Keep individual files to roughly 36,000 characters, about 15 to 20 pages. With up to 20 files specified, Copilot searches their full contents.

Because the agent is a file in Site Assets, it carries version history like any other library file.

11. Copilot Notebook, and publishing what it produces

Procedure 11

Permitted with a discipline attached
Microsoft 365 Copilot app  >  Notebooks  >  New notebook
  Add sources    (the specific files and pages for this one problem)
  Ask            (answers are grounded on that set only)
  Generate       (Word, Excel, PowerPoint output, or a mind map)

Then publish. A Notebook and its Pages live in a SharePoint Embedded container, not a site. The container does not appear in the SharePoint admin center site list, is bound to one user's identity, and has no library, no inherited permissions and no navigation. Purview reaches it, so it is not shadow IT, but nobody will find it.

The rule: the Notebook is where you think, the library is where the thinking lands. Save anything durable into the document library as a file before you close the notebook.

12. Connect Excel with Power Query

Procedure 12

Permitted client-side, no Power Platform
Excel desktop  >  Data  >  Get Data  >  From Online Services
                       >  From SharePoint Online List
  URL: the SITE url, not the list url
  Implementation: 2.0

Set every data type explicitly in the query editor. Left to itself, Power Query renders Yes/No columns inconsistently as TRUE/FALSE or 1/0 depending on the implementation version.

Questions for your IT Advisor

Six specific rulings that between them unlock or close off most of the gray area. Copy them into an email as they stand.

1. Standard connectors in a SharePoint-originated flow

Are SharePoint-triggered flows that use only Standard Microsoft 365 connectors (Office 365 Outlook, Microsoft Teams, Approvals, Office 365 Users, Excel Online (Business)) in scope, or must the flow use the SharePoint connector exclusively?

2. Send an HTTP request to SharePoint

Is this action permitted for SharePoint-only solutions, given that it reaches only the SharePoint REST API of the specified site, or does the breadth of the REST surface require review?

3. SharePoint agents versus Copilot Studio

Does the organisation agree that native SharePoint agents are governed by Copilot licensing rather than Power Platform citizen-development rules, and that Copilot Studio agents fall under Power Platform governance?

4. Office Scripts invoked by a flow

Is a flow-invoked Office Script in scope when the workbook is stored in the SharePoint library, or does involving the Excel Online (Business) connector place it outside?

5. Excel Online (Business) against SharePoint-resident workbooks

Where the workbook physically resides in a SharePoint document library, does reading and writing its tables count as interacting with SharePoint?

6. OneDrive for Business

Is OneDrive for Business considered part of the permitted SharePoint scope, given that it shares the same underlying platform, or is it a distinct location that falls outside?

Staged plan

Sequenced so that nothing in stage one waits on a governance answer.

Stage one, start now, no review required

Permitted
  • Consolidate onto a single SharePoint site and move shared-drive content into document libraries with content types, versioning and retention labels.
  • Convert recurring workbooks and reference data into SharePoint lists with indexed key and date columns. Stay under the 5,000-item view threshold from the start.
  • Use Rules for simple notifications, JSON column and view formatting for status and variance visibility, and content approval on controlled libraries.
  • Stand up the read-only SharePoint knowledge agent on the controlled document library.
  • Use Copilot in Excel and Word, and Excel Power Query with manual refresh, for analysis.

Stage two, build once the section C ruling lands

Confirm first
  • Build SharePoint-originated flows for intake, approval, reconciliation and reminders.
  • Design them SharePoint-connector-first, isolating any Outlook, Teams, Approvals or Office 365 Users step so it can be removed cleanly if ruled out.
  • Customise list forms using Integrate > Power Apps > Customize forms only.

Stage three, federated model only

Outside
  • Anything needing a premium connector, a standalone app or flow, Copilot Studio, Dataverse, SQL or Power BI.
  • Any reconciliation requiring a data source beyond SharePoint, including partner or enterprise systems. This is automatically out of boundary.
Thresholds that change the plan. If a list will exceed 5,000 items in a single view, redesign with metadata and filtered views before building. If a flow will exceed 6,000 actions per user per day, it needs a premium licence and therefore review.

Caveats

  • The wording "interacts only with SharePoint" is the decisive ambiguity. Every adjacent-connector step in this reference is flagged. Do not treat a "Confirm first" item as approved until an IT Advisor rules on it.
  • The 3 MB per-file SharePoint agent limit that circulates online is not supported by Microsoft documentation. The documented per-file grounding limits of 7 MB, 200 MB and 512 MB apply to Copilot Studio agents, not native SharePoint agents. The relevant figure for native agents is the 36,000-character optimisation guideline across up to 20 files.
  • Copilot in SharePoint remains a preview, not generally available, as of August 2026, and is unavailable in government and sovereign clouds. Its underlying model changed from Anthropic in the early 2026 preview to a Microsoft-managed OpenAI model. Treat any claim that it runs on Anthropic as outdated. The Anthropic sub-processor admin setting is a separate matter; the Anthropic independent-processor setting was decommissioned on 1 May 2026.
  • Feature status here goes stale quickly. The Copilot in-app licensing change (MC1253858) was announced for 15 April 2026, rescheduled to 16 May 2026, and applies fully only above 2,000 seats. Power Automate action caps are in a documented transition period. Verify before committing.
  • Retention-label auto-apply and several compliance features require E5, E5 Compliance or an add-on, not base E3. Confirm the exact SKU in use.
  • Native SharePoint agents cannot use Lists as a knowledge source, only sites, pages and document libraries. List-grounded question answering is a Copilot Studio or declarative-agent capability and falls outside the boundary.
  • Verdicts in this reference are an informed reading, not a ruling. Section C in particular records an interpretation, not a decision. The organisation's IT Advisor is the only authority on where the line falls.
