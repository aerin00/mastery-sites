Department build reference

Replacing email and the shared drive with a SharePoint Online master hub

An implementation-grade reference for a single-analyst build, constrained to what BC Hydro's partially federated Power Platform model actually permits.

00

Bottom line

Build one group-connected Team site, not subsites. Associate it to a hub only when a second workload site becomes necessary. Drive findability with a small managed-metadata schema plus configured Microsoft Search, because the same information architecture that fixes human search is what determines whether Copilot returns good answers or garbage.

Everything you need is achievable with native SharePoint Online plus list-native flows. Nothing in the target design requires stepping outside the permitted envelope.

The hard part is governance, not technology: permissions hygiene, retention, and keeping the record in SharePoint rather than in mailboxes, Loop, and OneDrive.

The three rules this whole build rests on

Rule 1 · Automation

If it is created from the list and touches only the list, it is allowed. Everything else goes to the IT Advisor before you build it, not after.

Rule 2 · Content lifecycle

Draft in OneDrive or Loop → collaborate in Teams → publish to SharePoint as the record. Only SharePoint is the system of record and the durable Copilot grounding layer.

Rule 3 · Migration

Do not lift and shift the mess. Assess, triage, and remediate first; migrating everything by default just relocates the chaos into a more expensive place.

The four escalation triggers

Route to the IT Advisor the moment a requirement involves any of these. Do not prototype first.

  1. A second data source of any kind, including another system's export landing anywhere but a SharePoint list.
  2. A recipient or system outside the SharePoint site.
  3. A user interface richer than a customised list form.
  4. A user population outside the PIC group.
02

Information architecture

Site type

A group-connected Team site is the correct primary container: shared membership, mailbox, Planner, and a document library, suited to a department that actively collaborates on files. A Communication site is a few-authors/many-readers broadcast surface; add one later if you want a polished landing page, and make that the hub home.

One-way door

A Team site cannot be converted to a Communication site or the reverse. Choose deliberately.

No subsites

Microsoft's guidance is explicit: in modern SharePoint, subsites are not recommended. Create one site per discrete topic, task, or unit of work, and create a separate site whenever security requirements differ. Deep hierarchies break on reorganisation and complicate migration, performance, and permissions.

One site or two

PatternUse whenCost
Single site — knowledge library plus the five lists together Start herePermissions for knowledge and forecasting are broadly the same populationLowest build and governance overhead for one analyst
Two sites plus a hub — Knowledge (read-mostly) and Operations (read/write)The knowledge library must be locked down independently, or a read-only portal experience is wantedSecond site to govern; hub to maintain

Split trigger: if you find yourself breaking permission inheritance on more than a couple of containers, stop and create the second site instead.

What a hub actually gives you

  • Shared navigation across associated sites, with a mega-menu up to three dropdown levels.
  • Shared theme and logo.
  • Rolled-up news and Highlighted Content across the hub.
  • Hub-scoped search.
What a hub does not give you

Permissions do not propagate. A limited Visitors-group sync exists but is capped at 10 users or groups and can take up to 4 hours. Plan permissions per site.

Hub caps: 2,000 hubs per tenant. Microsoft's PowerShell reference says "unlimited" associated sites; practitioners cite a practical ~1,000 and one supported nesting level. Registration changes can take 2–4 hours to appear.

Navigation

Three levels exist: global (tenant, via the app bar or home site), hub (across associated sites), and local (within a site). Keep local left navigation aligned to the 00–99 taxonomy so the knowledge library is predictable. Use audience targeting on navigation links and news so managers and analysts see different entries.

Provisioning consistency

Site templates and site scripts can enforce consistent columns, views, and navigation. At department scale with one builder, manually configuring one well-documented site is sufficient. Capture it as a written site charter so it is reproducible.

03

Metadata & findability

This is the section that actually solves "hard to find information", and the same work is what makes Copilot useful.

Folders and metadata together, not one or the other

The existing 00–99 folder taxonomy is legitimate and worth keeping. It gives humans navigable structure and partitions content below the view threshold. Metadata sits on top of it and does the finding.

  • Folders provide the partition and the navigation.
  • Columns provide the findability: Document Type, Process Area, Status, Review Date, System/Interface.
  • Default column values by folder mean a file dropped into 04_Work Instructions is tagged automatically. This is the single highest-leverage setting in the library, because tagging that depends on discipline does not survive contact with a busy team.
  • Metadata-driven views then cut across the folders: "everything due for review this quarter" regardless of where it sits.

Managed metadata

Use the term store for vocabularies shared across the knowledge library and the forecasting lists, such as Process Area and System/Interface names. Use local choice columns for list-specific status values. Keep the term store small; do not create terms for the sake of it.

Content types

Recommendation

Define content types locally on the site. A site owner can do this without SharePoint Admin rights and without tenant governance overhead.

The Content Type Gallery publishes tenant-wide only. There is no native "publish to just this one site"; a targeted push to hub sites exists but requires a pay-as-you-go licence and content types already published. Reserve the gallery for genuinely enterprise-reusable types. If a gallery content type in use is deleted, it converts to a local content type on the consuming site and keeps working.

Document Sets and Document ID

Both are Site Collection features that a Site Collection Administrator must activate; neither is on by default. The Document ID service assigns a permanent, human-readable ID that survives moves and renames within the site collection, with a 4–12 alphanumeric custom prefix.

Longevity caution

Document Sets frequently do not surface correctly from the modern Content Type Gallery and are best created locally within the site collection; Document Set Settings can be inaccessible even when published. Microsoft has signalled low ongoing investment. Do not make Document Sets structural to the design.

Versioning and approval

New libraries default to 500 major versions with FIFO trimming; the UI allows 100–50,000 and will not go below 100. An organisation-level default now exists, with automatic trimming by age capped at 500 versions per file.

Knowledge library setting

Enable major and minor (draft) versions with content approval. Readers see only published majors; drafts stay at 0.1, 0.2 with authors and approvers. This is what keeps 06_Future State and 07_Review Required out of the approved set that the Copilot agent grounds on.

Version history is not a backup. Versions die with a permanently deleted file after the 93-day recycle window.

Search configuration

Configure Microsoft Search in the Search & Intelligence admin centre. These are admin-curated and improve Copilot too, because Copilot calls the Graph search API at runtime.

  • Bookmarks — pinned answers for high-value queries ("forecast deadline", "JOUA process").
  • Acronyms — JOUA, JUAS, PIC, I&PC and the rest. Cheap, and disproportionately effective for a new joiner.
  • Q&As — short authoritative answers.
  • Verticals — a "Policies" vertical filtered to approved policy documents. Site-level verticals need the site search scope set appropriately; answers work at org scope.

Managed properties, search schema, and the PnP Modern Search web parts are available for advanced rollups, but out-of-box hub search plus verticals will very likely suffice at department scale.

04

Permissions & retention

Group model

Manage access through the site's Microsoft 365 Group and Entra ID security groups placed inside SharePoint permission levels. Use SharePoint groups (Owners / Members / Visitors) as the assignment mechanism and put security groups inside them. Do not add individuals.

Inheritance

Break inheritance as rarely as possible, at container level (library or list) only, never per file. For the knowledge library, set library-level permissions once with Visitors as read, rather than per-folder exceptions.

Silent inheritance breaks

Every "Share" or "Copy link" on an inheriting item can create a unique permission scope without anyone noticing. Set the default sharing link to "People with existing access", which never breaks inheritance. Turn Anyone links off.

Limit: up to 50,000 unique permission scopes per list or library; Microsoft recommends staying under 5,000. Inheritance changes are blocked above 100,000 items.

Copilot readiness controls

Copilot inherits user permissions exactly. If a user cannot already find a file through Microsoft Search, Copilot cannot surface, summarise, or reference it. That also means existing oversharing becomes over-surfacing the day Copilot lands.

Licensing

SharePoint Advanced Management is included once the tenant assigns at least one Microsoft Copilot licence. The exception is restricted site creation by apps, which still needs the SAM Plan 1 add-on.

Sensitivity labels

Apply container labels to the site and document labels to content. A label with encryption affects Copilot: by default Copilot cannot ground on content the user cannot decrypt at query time. Decide this deliberately and write the decision down.

Retention and the 99_Archive folder

MechanismScopeBest for
Retention policiesContainer (site or library), blanketA baseline "retain everything N years"
Retention labelsPer item, can be a library defaultDeclaring records, disposition review with human approval, proof of disposition

Back 99_Archive with a retention label rather than treating it as just a folder, so archived content is defensibly governed with a disposition review step. Two consequences to expect: labels can take up to 7 days to publish from Purview, and records marked via label cannot be edited or deleted until released.

Retention removes expired content from the searchable graph. Compliance deletion intentionally shrinks Copilot's grounding surface, which is correct behaviour, not a fault.

Governance artefacts to produce

  • Site charter: purpose, owners, audience, lifecycle.
  • Naming standards for files, folders, lists, and columns.
  • Metadata dictionary: every column, its term set, and who owns the vocabulary.
  • Roles and responsibilities, including who approves publication.
  • Review cadence for 06_Future State and 07_Review Required.
  • A logged exception for every broken inheritance, with reason and owner.

Migration off the drive

Tooling

ToolCostFit
SharePoint Migration Tool (SPMT) DefaultFreeFile share to SharePoint. Right choice at 10–100 GB. v4.0+ has the scan/assessment capability built in.
Migration ManagerFreeAgent-based, scales larger file-share jobs, adds cloud sources
ShareGate / AvePoint / QuestPaid (ShareGate Essentials from roughly USD 5,995/yr)Restructuring, richer metadata and permission handling, incremental passes, validation reporting. Likely unnecessary at this scale.
SMATFreeTargets on-prem SharePoint Server farms, not plain file shares. End of support 1 Oct 2026; capability moved into SPMT.

Assess and triage before moving anything

  • Scan for paths over 400 characters, invalid characters, and oversized files.
  • Identify ROT: redundant, obsolete, trivial. Run an aged-content analysis.
  • Classify every folder as migrate, archive, or delete/leave.
  • Map the existing folder structure to the 00–99 taxonomy and to metadata columns before the first wave.

Remediate

Fix filenames and invalid characters, and reduce folder depth, at source. The path budget is 400 characters decoded, and deep network drives routinely blow it.

What SPMT preserves

Supported metadata, and permissions when mapped via Entra lookup or a mapping file. Timestamps and authorship can be preserved for file shares.

Confirm before you commit

Unverified Version history preservation is not guaranteed on quick file-share transfers. If audit history matters for any folder, test that folder first and plan accordingly. SPMT will not redesign your architecture, clean content, set destination templates, or restructure anything.

Job limits: a source package producing more than 100 destination errors is blocked, and every valid file in that package is blocked with it. Keep under 5,000 queued jobs. Background migration is throttled harder during weekday daytime hours. Single move operations: max 100 GB / 30,000 files / 15 GB per file.

Waves and cutover

  1. Pilot one process area. Validate metadata, versions, and permissions before scaling.
  2. Migrate in waves aligned to the 00–99 structure.
  3. Announce the cutover date early and repeat it.
  4. Make the network drive read-only. This is the moment the project succeeds or quietly fails.
  5. Run a final delta pass, then decommission.

Migrating the email workflow

Replace "email an attachment" with "submit to a list". Convert recurring email intake to a list with a form. Keep a shared mailbox only where external senders genuinely require email, and turn those messages into list items so status and dates are tracked. This is exactly the pattern behind the Submission Tracker and Admin Change Requests lists.

List design for the forecast process

The five-list model is correct. Build it with:

  • Lookup columns relating Forecast Entries to Project Master and Forecast Cycles, so one entry per project per cycle is structurally enforced rather than remembered.
  • Column validation for anything a human can get wrong.
  • Conditional formatting on submission status so an overdue row is visible without opening it.
  • Customised list forms so submitters see only the fields they own.
  • List comments so discussion stays attached to the record instead of in a mailbox.
  • Indexed columns before the list reaches 5,000 items.

Automation, cheapest first

  1. Try a list rule. Needs only Edit permission.
  2. Try Set a reminder on the date column.
  3. Only then build a flow from the list's Automate menu.

Approvals: use SharePoint content approval with major/minor versioning for documents, and the Teams Approvals app or a list-created flow for process sign-off.

Audit trail

Stamp who and when on every state change through the list-native flow. This is the capability that replaces "search my sent items", and it is the argument that wins the change-management conversation.

07

Copilot & the app set

The governing rule

Draft in OneDrive or Loop → collaborate in Teams → publish to SharePoint as the record. Only SharePoint, and the tenant semantic index built from it, is the system of record and the durable grounding layer. Put this sentence in the governance doc.

How grounding actually works

Copilot orchestrates across Microsoft Graph and the semantic index and respects permissions exactly. The tenant-level index is generated automatically from text-based SharePoint files; a user-level index covers a personal working set. When a user points Copilot at a specific library or folder, column metadata is used as an additional relevance signal, which is the direct return on the work in section 03.

SharePoint agents

Every site has a ready-made agent scoped to the whole site, which cannot be edited, renamed, or deleted. A custom agent can be scoped to specific libraries, folders, or files and is read-only against that content. That is the right vehicle for the JUAS knowledge agent.

  • Scope it to the published knowledge content only. Exclude 06_Future State, 07_Review Required, and 99_Archive.
  • Creating an agent needs Edit permission plus a Copilot licence, or tenant pay-as-you-go billing.
  • Admins can suppress agents on a site via Restricted Content Discovery.
  • Keep referenced documents under roughly 36,000 characters (15–20 pages) for reliable retrieval, and strip complex tables. Unverified
Naming confusion to expect

The "Knowledge Agent" library organiser was rebranded to "AI in SharePoint" in 2026 and is in preview. It is a different thing from the Q&A agents, which are generally available.

The Teams structural warning

Every Team is backed by a SharePoint site collection. Standard channels map to folders in the parent site's default library. Private and shared channels each get their own separate SharePoint site collection, with independent permissions that cannot be managed from SharePoint and display as read-only.

Consequence

Every private channel proliferates a site and fragments retention, eDiscovery, and storage scope. Plan channel structure up front, and prefer standard channels. Also note the Teams file interface hides metadata columns, content types, and views, so do all document-management work in the SharePoint site directly.

Build order: SharePoint first, Teams second for conversation. Not the reverse.

08

Adoption & measurement

Getting a team off email and the drive

  • Pilot one process area rather than announcing a platform.
  • Recruit one or two champions who feel the pain of the current search problem most.
  • Train on two things only: tagging and list intake. Everything else is discoverable.
  • Enforce one hard rule: no new files on the shared drive, with the drive read-only from a stated date.
  • Architecture should mirror how people actually work, not the org chart.

Measurement

SignalSourceTells you
Visits, popular content, search queriesSite usage analyticsWhether the hub is being used at all
Zero-result queriesMicrosoft Search analyticsExactly which bookmarks and acronyms to add next. The highest-value report in the set.
Readiness, adoption, impact, sentimentCopilot Dashboard in Viva InsightsAvailable to any M365 business or enterprise customer with an active Exchange Online account, without a paid Viva Insights or Copilot licence to view. Data typically within 7 days of licence assignment.
Agent metricsAgent DashboardRequires 50 or more Copilot licences assigned plus agent activity. Likely out of reach at PIC scale.

Failure modes to design against

  • Recreating the deep folder maze in a new location.
  • No metadata governance, so tagging drifts and views stop working.
  • Breaking inheritance per file until permissions are unauditable.
  • Over-hubbing: creating hubs for structure that navigation would have solved.
  • Letting the team sync a large library to desktops.
  • Records living in Loop, OneDrive, or mailboxes.
  • Building automation outside the permitted envelope and having it pulled.
  • Deploying a Copilot agent over an overshared site.

Build sequence

Roughly 16 weeks, one analyst. Checkboxes are for working through the plan in a session; they are not saved.

0Weeks 1–3

Assess and design

  • Confirm licensing. At least one Copilot licence means SAM is available.
  • Run the SPMT scan on the network drive. Inventory ROT, long paths, invalid characters.
  • Finalise the metadata dictionary and local content types.
  • Write the site charter.
  • IT Advisor Confirm the four forecasting flows are in scope, and raise any external-notification requirement now.
1Weeks 3–6

Build the container

  • Provision the Team site.
  • Configure the knowledge library: 00–99 folders, metadata columns, default column values by folder.
  • Turn on major/minor versioning and content approval; set library permissions to read-mostly.
  • Build the five lists: columns, lookups, validation, views, indexed columns.
  • Configure Microsoft Search bookmarks and acronyms.
2Weeks 6–9

Pilot migration and automation

  • Migrate one process area as a pilot wave.
  • Validate metadata, version history, and permissions on the pilot before scaling.
  • Build the four list-native flows plus rules and reminders, from the lists.
  • Test the approval path end to end with a real submitter.
3Weeks 9–13

Full migration and Copilot enablement

  • Migrate the remaining waves.
  • Run the Data Access Governance report and remediate before any agent goes live.
  • Apply Restricted Access Control, sensitivity labels, and retention labels; set the 99_Archive label.
  • Create the custom read-only agent scoped to the published knowledge library.
  • Verify the agent cannot surface 06, 07, or 99 content. Test with a deliberately awkward question.
4Weeks 13–16

Cutover, adoption, measurement

  • Make the network drive read-only; run the final delta migration; decommission.
  • Train the group on tagging and list intake.
  • Publish the governance documents.
  • Stand up usage and Copilot dashboards; set the review cadence.
  • IT Advisor Route anything requested beyond SharePoint-only scope.

Verify before you build

Moving targets

  • "AI in SharePoint" (formerly Knowledge Agent) is in preview and was renamed during 2026.
  • Copilot Dashboard and Viva Insights unification, and Agent Dashboard general availability, are in flux.
  • SAM licensing has already shifted once. It is now bundled with Copilot, but some features still require Plan 1. Re-check at build time.

Where sources disagree

  • Hub association counts: Microsoft's PowerShell documentation says "unlimited"; practitioners cite roughly 1,000 and one nesting level. Treat the practitioner figure as design guidance, not a hard limit.
  • The content type "push versus pull" publishing model change is community-reported and traceable to a 2021 Syntex update, not clearly stated in core Microsoft documentation. Unverified
  • Several practitioner and vendor blogs corroborate Microsoft documentation but should not be treated as authoritative for limits. Where a number matters, confirm it on Microsoft Learn.

Decisions to make explicitly, not by default

  • Whether encryption-bearing sensitivity labels are applied, given the effect on Copilot grounding.
  • Whether list rules and reminders are accepted by your IT Advisor as inside the SharePoint-only exception.
  • Whether version history must survive migration for any specific folder, and testing that folder first if so.
  • Single site versus two sites plus a hub. Revisit at the end of Phase 1, when the real permission requirements are visible.
